# hw:request 設計書

本書は[hw:request](../../../plugin/skills/request/SKILL.md)の設計意図を書く。スキル本文とひな型（`assets/`）が定めることは書かず、それらを読んだだけでは読み取れない、なぜそうなっているかだけを書く。定めの現物はスキル本文とひな型にある。

## 位置づけ

- スキルとエージェントの境界は[設計書](../index.md)の「スキルとエージェントの境界」による。本スキルは、入り口（依頼内容、終点、自走レベル）と出口（終点の産物と完了報告）、進む道（7段階と成果物）と止まる条件（レビュー、裁定、利用者への提示）と、そこで残す記録だけを定める。段階の中の進め方は統括に委ねる。
- 統括のペルソナは`hw:mgmt-orchestrator`である。審議、裁定、出力の表記はペルソナが持つため、スキルは定め直さず参照する。プロジェクトの`CLAUDE.md`は参照先にしない。
- 担当に渡す資材は指示書、担当共通指示、指示書が列挙した記録だけである。担当に不要なファイルを読ませないためである。評価者と確認者だけはスキル本文を読む。固定観点と提案の要件がスキル本文にあるためである。担当共通指示に出力の表記を写しで持つのは、担当にペルソナのファイルを読ませないためである。

## 記録

- 記録をファイルに置いて正本とするのは、統括の記憶がトークン量の上限による中断で予告なく失われるためである。記録にないことは再開した統括に引き継がれない。「記録してから進め」はこの帰結である。
- 証跡を案件ファイルと計画ファイルから分けたのは、証跡が予想以上に増え、決定事項を持ち担当にも展開される`index.md`が肥大化したためである。証跡の用途は、中断から再開してセッションが変わっても統括が判断理由を辿れることに留める。
- 証跡を担当に渡さず指示書の読むべき記録にも入れないのは、担当が情報不足になったとき、担当が自ら証跡を辿るのではなく親である統括に問えばよいためである。
- 対応方針を案件ファイルから分けたのは、案件が終点によって調査、方針、計画、実行の四つに分かれ、終点までに要らない節を案件ファイルに持たないためである。計画はもともと分かれていた。
- 記録の書き方の定めをひな型ではなくスキル本文に置くのは、ひな型は案件に写して使われ、ひな型に書いた説明は写した時点で消えるためである。ひな型の山括弧は書く内容の指示に留める。
- 案件の置き場の名前を半角英数字に限るのは、報告のリンクから辿れなくなるためである。
- 一時ディレクトリの鍵を`mktemp`の乱数にするのは、同じ人物を別の作業や追加依頼で使い回しても被らないためである。ハーネスのセッションIDは統括と担当で同じ値であり、人物を分ける鍵にならない。担当の一時ディレクトリを案件の完了か中止まで消さないのは、報告が一時ファイルをパスで引くためである。
- ファイル表にあるファイルを`index.md`からリンクしないのは、担当に不要なファイルを読ませないためである。統括はスキル本文の表で辿れる。
- 状態に「通過」のような別の語を置かず、レビューファイル、裁定記録、完了報告ファイル、証跡を裏付けとするのは、状態を統括の自己申告ではなく記録で判じるためである。状態は段階の状態から読み取れるため、別の語は要らない。
- スコープ外、制約、レビュー観点を現在値と出所だけで持ち経緯を持たないのは、経緯はレビューファイル、裁定記録、証跡が持つためである。
- 記録を参照データとし、利用者の言葉を依頼原文、利用者の裁定、利用者のレビューの三つに限るのは、ペルソナの参照データの扱いの節による。統括が書いた方針や判断を利用者の指示と取り違えないためである。

## 担当

- 担当の表を正本とし、役割と種別を分けるのは、役割はスキルが固定し、種別（`subagent_type`）は案件ごとに統括が選ぶためである。
- 人物の制約はペルソナの審議の節「人物はセッションで数えよ」「生産者は評価者になるな」による。観点を出す人物、観点を確かめる人物、観点に従って評価する人物を分けるのは利用者の意図である。確認者を統括にしないのは、統括が観点を束ねる側であり、産物を生んだ人物にもなるためである。
- 担当共通指示を案件ごとに写すのは、案件固有の定めを足すためである。案件固有の定めは全担当に共通なので案件に一つ置き、担当ごとの指示書に繰り返さない。
- 担当がサブエージェントを起動して作業の一部を委ねられるのは、委ねられた作業をどう進めるかが担当に属するためである。担当は統括から直接指示された人物に限り、委ねた作業の責任は担当にある。委ねるときに共通指示と指示書を渡させるのは、統括が起動していない人物には共通指示の定めが自動では届かないためである。

## 手順

- 各段階のレビュー観点は、その段階を完了にしてよいかの観点である。旧版の`assets/viewpoints/`を廃止してスキル本文の各段階の節に置いたのは、観点はレビューする対象が書かれる場所に置くべきであり、調査、方針、計画、実行で異なる観点を案件ファイルに持たないためである。
- 段階6の全体検証は全計画の成果物の全体検証であり、案件の全体検証は無い。全体レビューが段階6のレビューそのものであり、その結果にレビューを置くとレビューへのレビューになるため置かない。計画が無い終点で段階6を対象外にするのはこの帰結である。
- 段階7にレビューを置かないのは、完了報告が案件の総括と状態の変更だけであり、終点の産物は終点の段階で承認を得ているためである。
- 案件の利用者レビューをフルオートだけに置くのは、他のレベルでは終点の段階のレビューに利用者が加わり産物を承認しているためである。フルオートでは利用者がどの段階のレビューにも加わらないため、完了報告の後に案件を利用者レビューで止め、差し戻しで対応できる状態にする。
- 案件の利用者レビューの差し戻しで同案件か新案件かの境を終点ごとに引くのは、手戻りの量で判じるためである。やり直す方が軌道修正より早い範囲を新案件にする。目的と対応方針は案件の前提条件であり、そこへ戻る手戻りはほぼ全部に近い。
- 新案件にするとき切り戻すのは、案件をリセットして最初からやり直すための下準備である。切り戻しを利用者に問うのは、切り戻しが利用者の指示に起因するためである。同案件か新案件かも最終的に利用者の判断を貰う。
- 新案件を別セッションで開始するプロンプトを返すのは、コンテキストをリセットして開始するためである。同じセッションに貼るかは利用者の選択である。プロンプトに元の案件へのリンクと説明を含めるのは、新しい案件から目的に遡れるようにするためである。
- 完了した案件を再開しないのは、完了後の依頼はその案件への追加であり、別案件として扱うためである。残りの文が無ければ、残論点・保留から課題化する。

## レビュー

- 案件の観点と計画の観点を評価者が提案し、確認者が確かめ、統括が写すのは、観点を出す人物、確かめる人物、評価する人物を分けるためである。最初の案件固有の観点を段階1の評価者が提案するのは、段階1が目的と背景を確かめる段階であり、目的と背景が定まる前に固有の観点は出せないためである。案件固有の観点は現状調査の結果でも変わるため、段階のたびに提案がある。
- 観点、スコープ外、制約に追加だけでなく変更と削除を置くのは、範囲を動かさないことが正しいとは限らないためである。範囲を広げなかったことで見つけるべきものを見落とす、範囲を狭めなかったことでやらなくてよいことまでする、という悪影響があるため、適切な範囲を常に探り続ける。
- 提案の採否を確認者が判じ、判じきれないものだけを裁定に上げるのは、自律で判じられるものまで利用者に問わないためである。裁定に一本化する案は、利用者に問う回数が増えるため退けた。
- 提案の確認に段階のレビュー観点を用いないのは、段階のレビュー観点が産物を対象に書かれており、提案は産物ではないためである。
- 差し戻しの上限を5回目にしたのは、実際に動かして、3回では収束せず4回目で収束することが何度かあったためである。期待値は3回以内の収束であり、余裕をもって5回とした。この観測は提案の仕組みを入れる前のものである。5回目を三役審議で裁くのは、産物と評価のどちらの当事者も裁けないためである。
- 利用者の差し戻しを回数に数えないのは、利用者の差し戻しが依頼の修正であり、評価者の指摘とは別だからである。
- 統括の自己評価と生産者の自己検証をレビューにしないのは、ペルソナの審議の節「生産者は評価者になるな」による。

## 裁定

- 利用者ドキュメントのうち運用手順を既決にするのは、ブランチの運用や外部トラッカーへのアクセス方法のように作業の進め方を定めた記述を、案件のたびに問い直さないためである。依頼がその運用手順の見直しを求めるときに既決にしないのは、既決にすると依頼と衝突するためである。運用手順以外の記述を既決にしないのは、ペルソナの参照データの扱いの節により、読み取った文書は利用者の指示ではないためである。
- 現物と食い違う記述を不明として問うのは、憲章の第三条により、文書が現物の代わりにならないためである。
- 手順が定めた問いを裁定から外し、`AskUserQuestion`を終点と自走レベルの問いだけに使うのは、ペルソナの裁定の節による。4つ以外の答えを問い直すのは、カスタムを廃止したためである。

## 自走レベル

- カスタムを廃止したのは、パターンが多すぎ、影響範囲も広すぎて対応しきれないためである。自由入力を細かい指定として受け入れる案を退けた。
- フルオート以外のすべてのレベルで終点の段階のレビューに利用者が加わるのは、終点が段階7より前で終わる案件でも、利用者が産物を承認してから完了にするためである。
- 利用者がレビューしない段階で統括の推奨を採用して進むのは、そのレベルで利用者が委ねた権限の内にあるためである。統括の採用を証跡に書き完了報告で一覧するのは、統括の採用が利用者の裁定ではなく、利用者が後から異議を述べられるようにするためである。

## 作業の終点

- 終点を読み取れないとき問う側へ倒すのは、終点を実行と誤れば依頼の範囲を越え、調査と誤っても利用者が伸ばせば済むためである。
- 終点の変更で段階1へ戻るのは、終点が変わると目的が変わるためである。
