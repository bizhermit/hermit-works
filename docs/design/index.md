# Hermit Works 設計書

## リポジトリ構成

```text
/                          # 保守側（非配布）
├── .claude-plugin/
│   └── marketplace.json   # マーケットプレイス定義
├── CLAUDE.md              # 本リポジトリ保守用の指示
├── LICENSE                # ライセンス全文の正本
├── docs/
│   └── design/            # 設計書（本ディレクトリ）
│       ├── index.md       # 全体の設計
│       └── skills/        # スキルごとの設計
├── scripts/               # 保守用スクリプト
└── plugin/                # 配布側（インストール時にコピーされる範囲）
    ├── .claude-plugin/
    │   └── plugin.json    # プラグインマニフェスト
    ├── LICENSE            # 配布用の写し
    ├── agents/            # エージェント
    ├── skills/            # スキル
    └── assets/            # 共通資材
```

## 保守文書の方針

本リポジトリの保守文書は、正本の写しを作らない。動作の正本は配布物の定義そのもの（スキルなら`SKILL.md`、エージェントならエージェント定義）であり、そこには実行に必要なことだけを置く。文書は、その定義からだけでは読み取れない箇所の補足に専念する。判定条件の根拠、境界条件、選ばなかった案とその理由などである。定義の内容を書き写さない。

文書に網羅は求めない。補うべきことが無ければ書かず、不完全なまま置いてよい。正本が単独で成立している限り、文書が欠けても動作の解釈は揺れない。網羅を求めれば、正本を直すたびに文書を追う手間が生まれ、追いきれなくなった時点で両者が食い違う。食い違った写しは、無い文書より悪い。

配布物ごとの設計書は、種別ごとのディレクトリに配布物の名前で置く。スキルは`docs/design/skills/`、エージェントは`docs/design/agents/`である。

## 規律の展開

本プラグインが前提とする規律を、利用者環境へ届ける仕組みの思想を記す。動作の仕様は`plugin/skills/init/SKILL.md`、運用上の注意は`docs/design/skills/init.md`を正本とし、本節には書かない。

### 規律は起動時に読まれる場所へ置く

規律は、セッションが始まった時点で効いていなければ意味がない。作業に着手してから途中で入る規律は、それまでの判断を縛れない。Claude Codeが起動時に読み込むのは、作業ディレクトリとその上位にある`CLAUDE.md`と`CLAUDE.local.md`である。スキルの本文は呼ばれたときにしか読まれず、規律の置き場所にはならない。だから規律は、これらのファイルへ節として展開する。

サブディレクトリに置いたものは起動時には読まれず、そこのファイルを読んだ時点で初めて入る。展開先を決める基準をgitのリポジトリルートに置くのはこのためである。リポジトリ内のどこから起動しても上位にあたるため、常に起動時に読まれる。

### 展開物は原稿のとおりに置き直す

原稿はプラグインが持ち、展開物の正本である。展開したものを利用者が運用に合わせて編集することは妨げないが、プラグインはその編集を守らない。節の同定は、見出し行に埋め込んだマーカー（`<!-- charter -->`等、記録キーと同一）で行い、内容は比較も記録もしない。編集を守ろうとすると、原稿との比較、過去の版の同定、利用者の編集かどうかの判別が要り、判別に失敗した残置物が両方のファイルに積み重なるためである。見出しの文言で同定しないのは、文言は表示であって識別子ではなく、原稿側で文言を変えた途端に旧見出しの節を見失うためである。マーカーは所有の印でもあり、利用者がマーカーを外した節はプラグインの管理から離れ、利用者の文章として扱われる。

再展開する節は、`CLAUDE.md`と`CLAUDE.local.md`の両方からマーカーで除去し、展開先へ置き直す。これにより、記録が壊れていても前回の配置がどうであっても、節は必ず展開先の1箇所に収束する。消える内容は実行時の報告に残し、必要な変更は利用者が入れ直す。`project`の展開先はgitの履歴からも拾い直せるが、`local`の`CLAUDE.local.md`と記録はgit管理外であり、クローンし直し等で失われうる。これは許容する。

### 追随の制御は節ごとのリビジョンで行う

再展開の要否は、使用範囲と節ごとのリビジョンだけで決まる。リビジョンはスキル定義に埋め込み、原稿を直したときに上げる。プラグインのバージョンは原稿以外の変更でも動くため、節の追随には使わない。

展開先の内容を記録すれば、利用者が編集したのか原稿が新しくなったのかを機械的に区別できる。それを採らないのは、同じ内容が記録と実物の二箇所に持たれ、食い違ったときにどちらが正本かを決める必要が生じるためである。リビジョンは内容の写しではないため、この問題を持ち込まない。

記録の`version`は追随には使わないが残す。`project`では記録がリポジトリで共有されるため、手元のプラグインが、チームで展開されたバージョンと一致しているかを判断できる。記録より古いプラグインでの実行は展開を巻き戻すため、`hw:init`はそこで止まる。

## 案件と計画

依頼を受けてから完了するまでの進行を、**案件**と**計画**の二層で扱う。本節はその思想を記す。ディレクトリ構成・ひな型・フローの規約は別途定める。

### 二層に分ける理由

依頼には「何を解決するか」と「どう進めるか」が混ざっている。前者を担うのが案件、後者を担うのが計画である。分けるのは、二つが確定する時期が違うからである。目的は依頼を受けた時点で定まるが、進め方は現状を調べ方針を決めたあとでなければ定まらない。前工程の結果を知らない時点で作ったタスク分解は空想であり、それを計画と呼ぶと以後の判断がすべて空想の上に乗る。案件は目的が定まった時点で立ち、計画は方針が定まってから中身を持つ。

1つの案件に複数の計画が属する。逆に、依頼が最初から進め方の指示である場合は、案件を持たない計画もありうる。案件が計画を持つのであって、計画が案件を含むのではない。

### 状態をファイルに書き出す理由

AIの文脈は有限であり、セッションを跨いで保たれない。進行状況を文脈の中だけで持てば、中断はそのまま再開不能な喪失になる。案件と計画の状態はファイルを正本とし、再開は思い出すのではなく読み直すことで行う。

置き場所は、利用者が確認し裁定できる場所、すなわち作業中のワークツリーの中とする。個人環境や、利用者の目に触れない領域へ退避させない。案件の進行は利用者が随時止めて向きを変えられるものであり、見えない場所で進む作業は裁定の対象になりえない。

進行記録は共有しない。使用範囲が`project`であっても、`.hw/cases/`と`.hw/plans/`はgitの管理外に置く。件数が増えやすく、共有すればリポジトリの履歴が作業の経過で埋まる。共有すること自体は妨げないが、推奨しない。

共有すべきものは、正式な文書とソースコードから読み取れる状態が正常である。作業ファイルを議事録として掘らなければ分からない、という状態は不健全であり、そこを共有して補うのは順序が逆である。担当者が代わったときに要るものは、案件の記録ではなく成果物の側に残っていなければならない。

### 状態は機械で読める形にする

再開と実行順の判定は、記述の解釈ではなく状態の読み取りで決める。解釈が要る形にすると、同じ記録から違う再開の仕方が導かれ、中断のたびに進行が揺れる。状態の語彙は全層で統一し、並列に回せるものは実行順を同じ値にすることで表す。依存関係の表現力よりも、判定が一意に決まることを優先する。この選択により、実際には並列にできるものが直列に落ちる場合があるが、潰れ方は必ず安全側に倒れる。

### 各層は直下の子までを見る

案件は、自身と、直下の計画・子案件の全体状態までを見る。計画の中のタスクは見ない。層をまたいで覗くと、同じ事実の更新経路が増え、どこが正本かが曖昧になる。同じ事実を二箇所に持たないことを原則とし、読みやすさのために写しを置く場合は、正本がどちらかを明示する。

### 規模が計画に収まらなければ案件を分ける

計画は一つの工程を回す単位である。独自の調査と方針の裁定を要する規模に達したものは、計画ではなく案件である。その場合は子案件として分ける。分割の判定軸は、独立して完了できるかどうかに置く。兄弟の結果を参照せずにゴールを書けるか、兄弟の完了を待たずに検収できるか、その子だけ完了して止まっても対象が壊れないかを見る。

### 裁定は読み手が必ず読む場所に置く

裁定は利用者に属する決定であり、AIの裁量では動かせない。動かせない決定の記録を、読まれるとは限らない場所へ置くべきではない。裁定待ちの論点と裁定の記録は、案件・計画それぞれの進行記録と同じファイルに同居させる。再開する者も評価する者も必ずそのファイルを読むため、読み漏らしという失敗の様式そのものを作らずに済む。

この同居が成り立つのは、裁定の効力が案件の内側に収まっているあいだである。案件を跨いで効く決定は、案件とともに閉じる記録には置けない。その扱いは次節に定める。

### 効力の範囲を広げるのは利用者だけである

裁定の効力は、それが下された案件・計画の内側に限る。「今回はこうする」を「今後もこうする」に変えることは、決定の中身を運ぶ作業ではなく、決定の効く範囲を広げる行為であり、利用者の決定に属する。案件の完了時にAIが自動で恒久化する形は採らない。書き取りから一語が落ちただけで、利用者が言っていない規律が生まれ、しかもそれを疑う機会は「既決を問い直すな」の側の規律が塞いでしまうためである。

案件を跨いで効かせると利用者が明示した決定は、利用者が指示する恒久の文書へ収める。仮置きの場は設けない。決定の効く範囲を広げることと、それを規律として書き下ろすことを同時に行わせ、書かれないまま効く決定を作らないためである。仮置きの場を設ければ、そこへ積むことが文書を整える作業の代わりになり、いつまでも収まらない決定が溜まる。収める先が用意されていなければ、その決定は案件の内側で終わる。次の案件で同じ裁定を繰り返したくなければ、収める先を用意するのは利用者の仕事である。

明示が無ければ、決定は案件とともに閉じる。次の案件で必要になれば改めて諮る。同じことを再び問う手間は残るが、言われていない規律が黙って効き続けるより安い。

### ひな型は正本、実体は作成時点で凍結する

ひな型の改訂は、すでに存在する案件・計画へ遡及させない。進行中の記録を後から新しい形式へ書き換えると、当時どういう材料で何を判断したかが失われる。実体は作成時点のひな型のまま完結させる。
