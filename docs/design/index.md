# Hermit Works 設計書

## リポジトリ構成

リポジトリは保守側と配布側の二層に分ける。配布側は`plugin/`の下に閉じ、マーケットプレイス定義が指す範囲（インストール時にコピーされる範囲）と一致させる。`plugin/`の外は本リポジトリの保守にだけ使うものであり、利用側には届かない。ファイルの一覧は次のとおり。

```text
/                          # 保守側（非配布）
├── .claude-plugin/
│   └── marketplace.json   # マーケットプレイス定義
├── .claude/
│   ├── settings.json      # 本リポジトリ自身でプラグインを有効にする設定
│   └── skills/
│       └── release/       # /release（本リポジトリのリリース手順）
├── CLAUDE.md              # 本リポジトリ保守用の指示
├── LICENSE                # ライセンス全文の正本
├── README.md              # プラグイン利用者向けの案内
├── docs/
│   ├── design/            # 設計書
│   └── maintenance.md     # 保守用のコマンドとスキルの一覧
├── scripts/
│   └── git-cleanup-branch.sh # リモートで消えた作業ブランチをローカルから掃除する
└── plugin/                # 配布側（インストール時にコピーされる範囲）
    ├── .claude-plugin/
    │   └── plugin.json    # プラグインマニフェスト
    ├── LICENSE            # 配布用の写し
    ├── agents/            # エージェント
    │   ├── worker.md      # hw:worker（実行者）
    │   └── reviewer.md    # hw:reviewer（評価者）
    ├── hooks/             # フック
    │   ├── hooks.json     # 起動時に作業品質の基盤を加えるフックの定義
    │   └── foundation.sh  # 作業品質の基盤をフックの出力の形にする
    ├── skills/            # スキル
    │   ├── request/       # hw:request
    │   │   ├── SKILL.md
    │   │   └── templates/ # 指示書の雛形
    │   └── execute/       # hw:execute
    │       ├── SKILL.md
    │       └── templates/ # 実行計画、報告、レビューの雛形
    └── assets/            # 共通資材
        └── foundation.md  # 作業品質の基盤（四節）の本文
```

設計の判断：

- ライセンス全文の正本はルートの`LICENSE`に置き、`plugin/LICENSE`はその写しである。配布物だけを受け取る利用側にも全文が届くようにするためであり、正本を一つに定めて写しを従わせる。

## 利用側の作業ディレクトリ

プラグインは利用側のプロジェクト直下の`.hw/`を作業ディレクトリとする。`.hw/`は`.gitignore`に加えることを推奨し、READMEでそのように案内する。ただしプラグインは強制できないため、追跡対象とするかは利用側の自由である。

```text
.hw/
├── instructions/      # 指示書（hw:requestの既定の出力先）
└── cases/             # 案件（hw:executeの作業ディレクトリ）
    └── <YYYYMMDD>_<slug>/
        ├── instruction.md     # 指示書の写し
        ├── plan.md            # 実行計画と経過
        ├── reviewer-<n>.md    # 全体レビュー
        ├── tmp/reviewer-<n>/  # 全体レビューの評価者の一時ファイル
        └── tasks/<NN>_<slug>/ # タスクごとの報告（worker-<n>.md）、レビュー（reviewer-<n>.md）、一時ファイル（tmp/worker-<n>/、tmp/reviewer-<n>/）
```

## スキル

### hw:request

依頼元の要望を、引数と対話を通して言語化し、指示書として残す。

- **入力**：引数（要望と出力先の指定）、対話での答え、定められた規則のうち外部トラッカーの使用を定めた記述
- **出力**：指示書一件。雛形は`plugin/skills/request/templates/instruction.md`
- **出力先**：指定（引数・対話）、運用で定められた外部トラッカー、既定（`.hw/instructions/`）の順で決める

設計の判断：

- 指示書は依頼元の言葉で書き、実施者の解釈・提案・調査結果を加えない。指示書は後続の作業（人またはAI）が目的を確かめる起点であり、そこに実施者の推論が混ざると、依頼と推論の区別がつかなくなるためである。引き出せなかったことは未確定事項に残す。
- 依頼原文を要約せずそのまま残す。各節の文がどこから来たかを遡れるようにするためである。
- 問いは、意向を聞く問い（節を満たすため、案を示す前に依頼元の考えを聞く）と、判断を求める問い（実施者が判じきれない事項、依頼元にしか決められない事項）に分ける。後者は課題を示し、方針を確かめ、案を示す三段で進め、推奨を既定値にしない。どちらも1件ずつ問う。
- 外部トラッカーは運用が決めることであり、プラグインは何も提供しない。設定ファイルの形式も、トラッカーごとの課題の作り方も定めない。プラグインが決めるのは、運用が外部トラッカーを定めていれば既定より優先する、という順序だけである。
- 出力先が異なっても内容は同一の指示書とする。表題を課題の題名に、本文を課題の本文に充てるだけであり、出力先ごとに内容の形式を変えない。
- 出力は依頼元の承認を得てから行う。承認が得られなければ問いを示したまま停止し、推測で補って進めない。出力先を独断で変えない。

### hw:execute

`hw:request`が作成した指示書を受け、実行計画を立て、計画のタスクごとに実行者に実施させ、評価者のレビューを経て成果物を仕上げる。

- **入力**：引数（指示書のパスまたは課題の識別子）、指示書、対話での答え、定められた規則のうち外部トラッカーの使用を定めた記述
- **出力**：成果物（指示書の対象と範囲の内の変更）と、案件ディレクトリの記録（指示書の写し、実行計画と経過、タスクごとの報告とレビュー、全体レビュー）。雛形は`plugin/skills/execute/templates/`
- **担当**：実行者`hw:worker`と評価者`hw:reviewer`。いずれも統括が`Agent`ツールで起動するサブエージェント

設計の判断：

- 指示書をそのまま実行せず、実行計画を立てて依頼元の承認を得てから実行する。指示書は依頼元の言葉で書かれた要望であり、何をどの順で行い何をもって確かめるかは実施者が具体化する部分である。その具体化を依頼元が確かめられる形（`plan.md`）にしてから動くことで、依頼と実施者の解釈の区別を保つ。承認後の計画の変更も同じく承認を要する。
- 統括は成果物を自分で作らず、計画、担当の起動、判定、依頼元との対話だけを担う。作る人物と確かめる人物と判定する人物を分けることで、自分の産物を自分で承認する形を避ける。
- タスクは成果物と完了条件が一つに定まる単位に分け、完了条件は現物で確かめられる形で書く。評価者の判定を、意見ではなく現物の検証に基づかせるためである。
- 実行者と評価者は起動のたびに新しい人物であり、前回の内容は記録で渡す。評価者は実行者の報告を信用せず自分で現物に当たる。記録をファイルに残すのは、担当が会話の文脈を持たないためと、判定の根拠を後から辿れるようにするためである。
- 担当は記録を書き先に自分で書き、返答は一行（実行者は結論とパス、評価者は判定、指摘と提案の件数、パス）だけを返す。統括が全文を返答で受け取って書き写すと、同じ全文が統括のコンテキストに二度載り（受け取った返答と、`Write`の引数）、写すための出力も要る。担当が書けば、全文を生成するのは担当の一回だけで、統括のコンテキストには読んだ分だけが載る。
- 統括が記録を読むのは、次の段を決めるのに要る節だけである。判断待ちなら判断を求める事項の節、差し戻しなら指摘の節、最後の報告では全体レビューの完了条件の検証の節と、提案のあるレビューの提案の節を、見出しで抜き出して読む。承認のレビューは読まずに採る。評価の評価を始めると切りが無いため、評価者の自己点検に任せる。
- 担当の一時ファイルは、統括が渡す一時領域（`tmp/worker-<n>/`、`tmp/reviewer-<n>/`）に置く。一時ファイルの要否は作業と対象によって変わるため禁じず、置き場を`.hw/cases/`の下に閉じ込める。役割と回ごとに分けるのは、評価者が実行者の確かめの道具を使い回さず、自分で現物に当たるためである。
- 記録の名前は書いた役割で付ける（`worker-<n>.md`、`reviewer-<n>.md`）。Claude Codeのハーネスは、サブエージェントが`Write`で`report`、`summary`、`findings`、`analysis`で始まる`.md`を書くことを拒む（2.1.274の実行ファイルで確かめた。公式の説明は無い）。役割名で揃えるとこの判定に掛からない。これは「報告は返答で返せ」というガードレールを避ける形であり、依頼元がそれを承知で選んだ。
- レビューの判定は承認と差し戻しの二値であり、差し戻しの根拠は、完了条件の未達または検証不能、境界の外の変更、報告と現物の不一致の三つに限る。重大度の段階や観点の一覧は持たない。判定の基準を計画（完了条件と範囲）に固定し、評価者の裁量で基準が増えないようにするためである。該当しない指摘は提案として残し、採るかは依頼元が決める。
- 指摘と提案には確度（0から100）を付す。確度は判定に用いず、その内容が成り立つと評価者が判じる度合いを示す。提案には完了条件の外にある不具合と好みの改善が同じ形で並ぶため、依頼元が採否を決めるときに事実と好みを見分ける材料として付ける。
- 評価者には実行者と同じ制約を渡す。制約を知らない評価者は、制約のために採られた手段や制約のために変更されなかった点を、完了条件の未達や改善の余地として指摘してしまうためである。
- 差し戻しの繰り返しは同じタスクで3回までとし、それに達したら依頼元に判断を問う。差し戻しが繰り返される原因は計画（完了条件や範囲の書き方）にあることが多く、実行者の再試行では解けないためである。
- 実行者は、計画に無い要件や設計の判断が要ると分かったら決めずに止まり、統括が依頼元に問う。判断は依頼元にあり、担当にも統括にも無い。
- 評価者は成果物を変更しない。実行者はサブエージェントを起動しない。役割の境界をエージェント定義（`disallowedTools`）でも支える。実行者が起動した担当の作業は記録に残らず、実行者が自分で起動した評価者の承認は本スキルの評価に数えないためである。
- 実行者は、変えてよい範囲の内でも作業に要る変更だけを行い、作業の外で気づいた問題と、与えられたものが現物と食い違った箇所を報告の気づいたことの節に書く。統括はそれを最後の報告で依頼元に渡す。ついでの変更はレビューの対象を広げ、自分で切り抜けた食い違いは黙っていると次の実行者が同じ所で躓くためである。
- 計画が定めるのはゴールと制約であり、手段は担当がその内で選ぶ。依頼元が定めていない手段を計画に書けば、統括が制約を加えることになり、越権になるためである。スキルもこの手段の一つであり、名指しして扱わない。
- 統括は、担当の作業に要るもの（作業、目的、完了条件、制約、変えてよい範囲、読む資料、返答の形）を`plan.md`から取り出してプロンプトで渡し、`plan.md`と案件ディレクトリの構成は渡さない。担当は呼び出し元を限らない汎用の人物であり、呼び出し元が何者かや経緯を知ることは、担当の役割の外にあるためである。
- 作業の終点は指示書が定める。コミット、プッシュ、PRの作成、提出等の後処理は、指示書が求めていない限り行わない。成果物は作った場所に残し、その先（提出等）は依頼元が決める。

## エージェント

エージェントは呼び出し元を限らない汎用の担当である。役割ごとに一つの定義を持ち、作業の内容、制約、返答の形は定義に書かず、呼び出し元から与えられる。定義は計画、統括、`hw:execute`に言及しない。[作業品質の基盤](#作業品質の基盤)の四節は定義に持たず、起動時のフックで加わる。

- **hw:worker**：実行者。与えられた作業を、与えられた完了条件と制約の内で行い、完了条件ごとの検証結果を与えられた形で報告する。判断が要れば決めずに止まる
- **hw:reviewer**：評価者。与えられた成果物を、完了条件、制約、変えてよい範囲に照らして現物で確かめ、承認か差し戻しかを判定し、与えられた形でレビューする。成果物を変更しない

## 作業品質の基盤

作業品質の基盤は四節（憲章、参照データの扱い、出力の表記、報告前の自己点検）からなる。本文は`plugin/assets/foundation.md`の一つだけに置く。

プラグインが有効なセッションでは、フック（`plugin/hooks/hooks.json`）が起動時に四節を加える。

- **`SessionStart`**：主会話の起動時（`startup`、`resume`、`clear`、`compact`、`fork`のすべて）
- **`SubagentStart`**：すべてのサブエージェントの起動時。`matcher`を付けず、`hw:worker`、`hw:reviewer`、`general-purpose`等を区別しない

`foundation.sh`が`foundation.md`を読み、`hookSpecificOutput`の`additionalContext`として出力する。四節はシステムプロンプトではなく、会話の先頭のメッセージに添付として加わる。

設計の判断：

- 四節を届ける手段として、フックを選んだ。主会話とサブエージェントのいずれにも、出力スタイルや`agent`設定の枠を使わずに届けられる。本文を一つのファイルに置けるため、エージェントやスキルに逐語の写しを持たせずに済む。
- 出力スタイルと`agent`設定は採らない。いずれも一つしか設定できず、プラグインが使えば利用側がその枠を自分で選ぶ自由を奪うためである。出力スタイルはサブエージェントに届かず、`agent`設定は主会話のシステムプロンプトをエージェントの本文に置き換え、Claude Codeの既定の指示を丸ごと失う。
- フックはプラグインが有効な限り常に走り、利用側で外す手段をプラグインは用意しない。外したい利用側は、`CLAUDE.md`等で扱う。
- `additionalContext`は1万文字を超えるとディスクに逃がされ、モデルには先頭の一部とファイルのパスだけが渡る。四節は1万文字未満に保つ。
- 主会話は要約（compaction）の後も`SessionStart`で四節を入れ直せるが、サブエージェントの`SubagentStart`は起動時の一度だけである。サブエージェントの会話が要約されると、四節が要約に呑まれうる。
- `foundation.sh`は`sh`と`awk`で動く。JSONのエスケープは`\`、`"`、タブ、改行だけを扱い、他の制御文字を`foundation.md`に含めない。
