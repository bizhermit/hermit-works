# Hermit Works 設計書

## リポジトリ構成

リポジトリは保守側と配布側の二つに分ける。配布側は`plugin/`の下にだけ置き、マーケットプレイス定義が指す範囲（インストール時にコピーされる範囲）と一致させる。`plugin/`の外は本リポジトリの保守にだけ使うものであり、利用側にはコピーされない。ファイルの一覧は次のとおり。

```text
/                          # 保守側（非配布）
├── .claude-plugin/
│   └── marketplace.json   # マーケットプレイス定義
├── .claude/
│   ├── settings.json      # 本リポジトリ自身でプラグインを有効にする設定
│   └── skills/
│       └── release/       # /release（本リポジトリのリリース手順）
├── CLAUDE.md              # 本リポジトリ保守用の指示
├── LICENSE                # ライセンス全文の正本
├── README.md              # プラグイン利用者向けの案内
├── docs/
│   ├── design/            # 設計書
│   │   ├── index.md       # 設計書の全体
│   │   └── skills/        # スキルごとの設計書
│   │       ├── request.md
│   │       ├── execute.md
│   │       ├── skillify.md
│   │       └── visualize.md
│   └── maintenance.md     # 保守用のコマンドとスキルの一覧
├── scripts/
│   └── git-cleanup-branch.sh # リモートで消えた作業ブランチをローカルから掃除する
└── plugin/                # 配布側（インストール時にコピーされる範囲）
    ├── .claude-plugin/
    │   └── plugin.json    # プラグインマニフェスト
    ├── LICENSE            # 配布用の写し
    ├── agents/            # エージェント
    │   ├── worker.md      # hw:worker（実行者）
    │   └── reviewer.md    # hw:reviewer（評価者）
    ├── hooks/             # フック
    │   ├── hooks.json     # 起動時に作業品質の基盤を加えるフックの定義
    │   └── foundation.sh  # 作業品質の基盤をフックの出力の形にする
    ├── skills/            # スキル
    │   ├── request/       # hw:request
    │   │   ├── SKILL.md
    │   │   └── templates/ # 指示書の雛形
    │   ├── execute/       # hw:execute
    │   │   ├── SKILL.md
    │   │   └── templates/ # 対応方針と実行計画、報告、レビューの雛形
    │   ├── skillify/      # hw:skillify
    │   │   └── SKILL.md
    │   └── visualize/     # hw:visualize
    │       ├── SKILL.md
    │       ├── json-format.md # <案件>.jsonの形
    │       ├── scripts/   # <案件>.jsonの形の確かめ、セッション記録の集計、HTMLの描画
    │       └── pricing.json # 単価表
    └── assets/            # 共通資材
        └── foundation.md  # 作業品質の基盤（五節）の本文
```

設計の判断：

- ライセンス全文の正本はルートの`LICENSE`に置き、`plugin/LICENSE`はその写しである。配布物だけを受け取る利用側にもライセンスの全文を渡すためである。正本は一つに定め、写しは正本に合わせる。
- スキルとエージェントの本文には振る舞い（何を、いつ、どの順で行うか）だけを書く。意図と理由は設計書（`docs/design/`）の「設計の判断」に書く。本文に理由が混ざると、理由が変わるたびに本文が変わり、振る舞いの変更と区別がつかなくなるためである。

## 利用側の作業ディレクトリ

プラグインは利用側のプロジェクト直下の`.hw/`を作業ディレクトリとする。`.hw/`は`.gitignore`に加えることを推奨し、READMEでそのように案内する。ただしプラグインからは強制できないため、gitで追跡するかは利用側が決める。

```text
.hw/
├── instructions/      # 指示書（hw:requestの既定の出力先）
├── analysis/          # 可視化のHTMLとJSON（hw:visualizeの出力先）
└── cases/             # 案件（hw:executeの作業ディレクトリ）
    └── <YYYYMMDD>_<slug>/
        ├── instruction.md     # 指示書の写し
        ├── plan.md            # 対応方針、実行計画と経過
        ├── reviewer-<n>.md    # 全体レビュー
        ├── tmp/reviewer-<n>/  # 全体レビューの評価者の一時ファイル
        └── tasks/<NN>_<slug>/ # タスクごとの報告（worker-<n>.md）、レビュー（reviewer-<n>.md）、一時ファイル（tmp/worker-<n>/、tmp/reviewer-<n>/）
```

## スキル

各スキルの設計（入出力、設計の判断、処理フロー）は個別の設計書にある。

- [hw:request](skills/request.md)：依頼元の要望を、引数（要望または相談）と対話を通して言語化し、指示書として残す。
- [hw:execute](skills/execute.md)：指示書を受け、対応方針を立てて依頼元の承認を得たうえで、実行計画を立て、計画のタスクごとに実行者に実施させ、評価者のレビューを経て成果物を仕上げる。
- [hw:skillify](skills/skillify.md)：`hw:execute`の案件記録（`.hw/cases/`）を分析し、複数の案件に繰り返し現れるパターンを割り出し、依頼元が選んだものをプロジェクトのスキル（`.claude/skills/`に置くスキル）にするための指示書を作る。
- [hw:visualize](skills/visualize.md)：`hw:execute`の案件記録（`.hw/cases/<案件>/`）から、案件で使った資源、進め方、質を集めてHTMLに可視化し、案件一覧の`index.html`を作り直す。

## エージェント

エージェントは呼び出し元を限らない汎用の担当である。役割ごとに一つの定義を持ち、作業の内容、制約、返答の形は定義に書かず、呼び出し元から与えられる。定義は計画、統括、`hw:execute`に言及しない。[作業品質の基盤](#作業品質の基盤)の五節は定義に持たず、起動時のフックで加わる。

- **hw:worker**：実行者。与えられた作業を、与えられた完了条件と制約の内で行い、完了条件ごとの検証結果を与えられた形で報告する。判断が要れば決めずに止まる
- **hw:reviewer**：評価者。与えられた成果物を、完了条件、制約、変えてよい範囲に照らして現物で確かめ、承認か差し戻しかを判定し、与えられた形でレビューする。成果物を変えない

## 作業品質の基盤

作業品質の基盤は五節（憲章、参照データの扱い、出力の表記、報告前の自己点検、問い方）からなる。本文は`plugin/assets/foundation.md`の一つだけに置く。

「問い方」は、選択肢提示ツールを使う条件、問いの文の改行、問いの手順からなる。

- **選択肢提示ツール**：`AskUserQuestion`等を使うのは、事前に選択肢が定められた問い、または使うと明記されている場合だけとする
- **問いの文**：意味の切れ目で改行する
- **問いの手順**：依頼元の意見・対応案を引き出すため、段階的に問う。1.問題とその影響範囲、原因を示して意見・対応案を問い、この段階で案は示さない。2.答えが対応案でなければ、意見を言語化して方針を確かめた後、対応案、利害得失、推奨案を示し、対応案が決まるまで対話で引き出す。3.採用する対応案が問題を解決しているかを確かめ、矛盾点や未解決事項があれば問う。4.最終対応案を示し、承認を得る

プラグインが有効なセッションでは、フック（`plugin/hooks/hooks.json`）が起動時に五節を加える。

- **`SessionStart`**：主会話の起動時（`startup`、`resume`、`clear`、`compact`、`fork`のすべて）
- **`SubagentStart`**：すべてのサブエージェントの起動時。`matcher`を付けず、`hw:worker`、`hw:reviewer`、`general-purpose`等を区別しない

`foundation.sh`が`foundation.md`を読み、`hookSpecificOutput`の`additionalContext`として出力する。五節はシステムプロンプトではなく、会話の先頭のメッセージに添付として加わる。

設計の判断：

- 五節を届ける手段として、フックを選んだ。主会話とサブエージェントのいずれにも、出力スタイルや`agent`設定を使わずに届けられる。本文を一つのファイルに置けるため、エージェントやスキルに本文をそのまま写さずに済む。
- 出力スタイルと`agent`設定は採らない。いずれも一つしか設定できず、プラグインが使えば、利用側が自分で選んで設定できなくなるためである。出力スタイルはサブエージェントに届かない。`agent`設定を使うと、主会話のシステムプロンプトがエージェントの本文に置き換わり、Claude Codeの既定の指示がすべて無くなる。
- 問いの進め方（「問い方」の節）は、スキルの定義に書かず、フックで届く基盤に置く。プラグインが提供するスキルすべてに同じ進め方で問わせるためである。スキルが増えても進め方を書き写さずに済み、スキルの定義には何を問うかと問いと答えを書く場所等、そのスキル固有の事項だけが残る。
- フックはプラグインが有効な限り常に実行され、利用側で外す手段をプラグインは用意しない。外したい利用側は、`CLAUDE.md`等で扱う。
- `additionalContext`は1万文字を超えるとディスクに書き出され、モデルには先頭の一部とファイルのパスだけが渡る。五節は1万文字未満に保つ。
- 主会話は要約（compaction）の後も`SessionStart`で五節を入れ直せるが、サブエージェントの`SubagentStart`は起動時の一度だけである。サブエージェントの会話が要約されると、五節の内容が要約の中で失われることがある。
- `foundation.sh`は`sh`と`awk`で動く。JSONのエスケープは`\`、`"`、タブ、改行だけを扱い、他の制御文字を`foundation.md`に含めない。
