description: 対象タグのリリースノートドラフトを作成し、GitHub Releaseへドラフト登録する（/release 手順10からの続き、または単独起動）
---

このリポジトリ（hermit-works）のリリースノート作成を進めます。あなたは mgmt-release（リリースマネージャー）として振る舞ってください。

このコマンドはリポジトリローカルの保守用コマンドです（`.claude/commands/` 配下。プラグイン配布物の
`commands/` には含まれず、`hw:` 名前空間にも属しません）。`/release` の手順10（タグ作成確認）の後に
続けて実行することを想定していますが、対象タグさえ確定していれば別セッションから単独で起動しても
構いません。

対象タグ: `$ARGUMENTS`（例: `v0.5.0`）。省略された場合は `git describe --tags --abbrev=0` で最新タグを
対象にする。タグが1つも無い場合は、その旨を報告してここで中断する（以降の手順は実行しない）。
`$ARGUMENTS` が `-` から始まる場合は、オプションと誤解釈される恐れがありタグ名としても不正の可能性が
高い（本リポジトリのタグは `v` 始まり）ため、状況を報告してここで中断する。

## 手順

1. **ガード確認**: 対象タグの存在確認を次の順で行い、結果に応じて分岐する。
   - ローカル（`git tag -l -- <タグ>`）に存在するか確認する。
   - リモート（`git ls-remote --tags origin "refs/tags/<タグ>"`。release.md 手順10と同じ完全一致形式。
     部分一致の `grep` は誤判定の恐れがあるため使わない）に存在するか確認する。
   - (a) ローカル・リモート双方に存在する場合: そのまま手順2へ進む。
   - (b) ローカルに無くリモートにのみ存在する場合: `git fetch origin --tags` でローカルに取り込んでから
     手順2へ進む。
   - (c) ローカルにのみ存在しリモートに無い場合: 手順5で `--target` を付与する前提で手順2へ進む
     （この場合、タグのリモートへの push は行わない。制約節参照）。
   - (d) ローカル・リモートいずれにも存在しない場合: 状況を報告してここで中断する（以降の手順は
     実行しない）。
   - 上記のいずれで続行する場合も、あわせて `gh release view <タグ>` で同名の GitHub Release
     （ドラフト含む）の有無を確認する。既存のものがあれば上書きせず、状況（既存リリースの状態）を
     報告して利用者に指示を仰ぐ（この場合は以降の手順には進まない）。「リリースが存在しない」旨の
     応答以外のエラー（認証切れ・ネットワーク不通等）が返った場合も、状況を報告してここで中断する。

2. **材料収集**: `CHANGELOG.md` の対象タグに対応する節を正の材料として取得する。あわせて直前タグの
   特定（`git describe --tags --abbrev=0 <タグ>^` で対象タグの1つ前のタグを取得する。対象タグが
   最初のタグでエラーになる場合は「直前タグ無し」とみなし、対象タグまでの全履歴を範囲とする）を
   行ったうえで、直前タグ〜対象タグの差分（`git log <直前タグ>..<タグ> --oneline` 等。直前タグ無しの
   場合は `git log <タグ> --oneline`）を補助材料として取得する。`CHANGELOG.md` に該当節が見つからない
   場合は、その旨を報告したうえで、差分のみからのドラフトになる旨を明示して続行する。

3. **ドラフト作成**: 過去の GitHub Release（例: v0.2.0）の体裁に準拠して本文を作成する。
   - 見出し `# hermit-works vX.Y.Z` の下にリード文（今回のリリースの要点を2〜3文で）を置く。
   - 「## 新機能」に太字の小見出し＋箇条書きで主要な変更を記載する（機能追加が無い場合は省略可）。
   - 必要に応じて「## そのほかの改善」「## 修正」「## 変更にあたっての注意事項」を続ける
     （該当しない節は省略してよい）。
   - 末尾に「インストール・更新方法は README をご覧ください。」等、README への誘導を1行添える。
   - 文体は「です・ます調」で統一する。
   - 記載対象は利用者面資材（`agents/`・`commands/`・`skills/`・`.claude-plugin/plugin.json`・
     `README.md`）の変更を中心とする。保守面資材（`.claude/`〔保守用スクリプト `.claude/scripts/`
     を含む〕・`.github/` 等）のみの変更は
     原則ノートに載せない（載せる場合も「そのほかの改善」に簡潔に留める）。

4. **承認**: ドラフト全文を提示し、利用者の承認を得る。承認が得られるまで手順5には進まない。

5. **登録**: 承認後、GitHubへドラフトリリースとして登録してよいか**個別に**確認を得てから、
   一時ファイル（スクラッチパッド等の非リポジトリパス）にドラフト本文を書き出し、
   `gh release create <タグ> --draft --title "hermit-works <タグ>" --notes-file <一時ファイル>` を
   実行する。手順1(c)（ローカルにのみ存在しリモートに無い）の場合は `--target <タグの指すコミットSHA>`
   を付与する（ドラフトの段階ではタグ自体は作成されず、公開時に GitHub 側で作成される。タグの
   リモートへの push はここでは行わない）。`--target` 指定が gh トークンの `workflow` スコープ不足で
   拒否された場合は、`gh auth refresh -h github.com -s workflow` の実行かタグ push のいずれかを
   利用者に提案し、ここで中断する。

6. **完了報告**: 登録結果（ドラフトの URL）と、公開（publish）は利用者が GitHub 上で行う旨を報告する。
   手順1で中断した場合は、その旨と理由のみを報告する。

## 制約

- 公開（publish）は行わない。GitHub Release のドラフト登録までがこのコマンドの範囲。
- 既存の GitHub Release（ドラフト・公開済み問わず）の編集・削除は行わない。
- タグのリモートへの push は行わない（手順1(c)でローカルのみに存在するタグを対象にする場合を含む）。
- 各ステップの確認は個別に行い、まとめて先取りの承認を得たものとして省略しない。
