# Claude Code permissions パターン運用ガイダンス

Claude Code の権限設定（`.claude/settings.json` 等の `permissions`）を提案・変更・レビューする際に参照する、
Bash パターンマッチングの仕様、Edit()/Read() のパスルールとしてのパス glob（permissions のパスルール
として評価されるのはこの2つのみ。Write() 等は受理されても参照されない）、Write() 等の実ツール呼び出し
全般に適用される hooks の `if:` 条件の仕様、および deny ルール提案時に踏むべき確認手順をまとめる。

背景: 過去に `deny: Bash(git push --force*)` のような前方一致パターンが `--force-with-lease` による
正当な運用を意図せず巻き込み、事故になった事例がある（原因は末尾 `*` の直前にスペースが無いパターンが
単語境界を持たないことの見落としと、既存 deny の書き分けを差分確認せず丸ごと置換したことの2点）。

## 規則（Bash パターンマッチング・パス glob・permissions・sandbox の仕様）

1. Bash パターンは（複合コマンドの分割・固定ラッパー除去後の）コマンド文字列全体への前方一致である。
   末尾 `*` の直前にスペースが無い形は単語境界を持たず、より長いオプション名も巻き込む
   （例: `Bash(git push --force*)` は `--force-with-lease` にも一致する）。スペース付き
   `… --force *` はプレフィックス直後がスペースまたは文字列末尾の場合のみ一致し、引数なし単体形も
   これに含まれる（そのため単体形専用の deny 行を別途用意する必要はない）。
2. 表記ゆれを広く吸収する意図と、オプションを個別に切り分ける意図はパターンごとに逆向きの判断になる
   ため、提案時にどちらを意図しているかを明示する。
3. deny は deny→ask→allow の評価順で最優先され、具体性やスコープ（enterprise/CLI/local/project/user
   等）を問わずどのレベルの allow でも緩められない。提案前に、そのパターンに一致してしまう正当な
   コマンドを列挙し、利用者側の手順・スクリプト・文書に記載されたコマンドを止めてしまわないかを
   検索・確認する。
4. 既存の permissions を書き換える場合は新旧差分を必ず提示する。既存の書き分け（複数行に分かれた
   パターン等）は前任による切り分けの記録として扱い、崩す場合は理由を明示する。この確認は
   permissions に限らず、設定・チェックリスト・手順書を丸ごと置き換える作業全般に適用する。
5. 引数を制約する Bash パターンは回避されうる（オプションの前置、コマンド前半の差異〔例:
   `git -C <dir> push …` は素の `git push …` 向けパターンに一致しない〕等）ことを前提とし、確実な
   制約が必要な場合は中間ワイルドカードの活用や hooks 等の他レイヤーとの併用を検討し提案に含める。
6. **（本規則のみ出典区分が異なる: 公式ドキュメント確認のみ・実機未検証。「注意」節参照）**
   sandbox 設定（`sandbox.filesystem`/`sandbox.network` 等）は permissions とは効く層が異なる
   制約であり、OS レベルのサンドボックス境界で強制される。Claude Code が判定するコマンド文字列
   だけでなく、kubectl・terraform・npm 等その配下で起動される**すべてのサブプロセス**に適用される
   ため、規則5で挙げたような Bash パターンのすり抜け（コマンド前半の差異等）の影響を受けない。
   一方で OS 依存の機構（bwrap 等）に依存するため、依存ツールが環境に無い場合は sandbox 自体が
   無効化され、制約なしの実行に戻る（フェイルオープン）。この特性上、permissions・hooks 等の
   既存の制約を代替・降格する根拠にはせず、その上に重ねる加算の選択肢としてのみ提案する。
   - `sandbox.network.allowedDomains` / `deniedDomains`: 許可・拒否ドメインを指定する。両方に
     一致する場合は `deniedDomains` が優先される。`deniedDomains` は全設定ソースからマージされる
     と公式ドキュメントに明記されている（`allowedDomains` にはソース制限の記載がない）。他の
     設定ソース限定は後述「設定したつもり事故」参照。
   - `sandbox.network.strictAllowlist`（v2.1.219 で追加）: 許可リスト（`allowedDomains` 等）外の
     ホストへのアクセスを、承認プロンプトを出さずに拒否する設定である。sandbox 内で実行される
     コマンドのみを対象とし、WebFetch 等の Claude Code インプロセスで実行されるツールには
     適用されない。有効な設定ソースの制限は後述「設定したつもり事故」参照。
   - `sandbox.credentials`（`sandbox.credentials.files[]`＝`path`+`mode`、
     `sandbox.credentials.envVars[]`＝`name`+`mode`。配列は全設定ソースから
     マージされる）: 共通ガードレール（認証情報の値を転記しない）を機械層で裏打ちする手段として
     提案できる。`mode: "deny"`
     （v2.1.187 以降）を提案の主軸とし、files はサンドボックス内からの読み取りをブロック
     （`filesystem.denyRead` と同じ効果。この効果は `filesystem.disabled` 下では失われる。後述
     「設定したつもり事故」参照）、envVars はサンドボックス実行コマンドの環境から変数を
     除去する。`mode: "mask"` は認証を通したまま値を隠す選択肢だが、`network.tlsTerminate`
     （実験的機能）が必須・必要バージョンが envVars（v2.1.199 以降）と files（v2.1.221 以降）で
     異なる・有効な設定ソースが限定される・プラットフォーム差があるなど前提が多く、運用の詳細は
     公式ドキュメントを参照する（要点は後述「設定したつもり事故」参照）。対象範囲はサンドボックス
     実行の Bash コマンドのみで、組み込みの拒否リストは無く列挙した対象のみが保護される。
     `credentials.allowPlaintextInject`（v2.1.199 以降、既定 false）は平文 HTTP へのマスク差し
     替えも許可する緩和方向の設定であり、`filesystem.disabled` と同様に本ガイダンスでは
     **提案しない**。利用者環境で既に有効になっていないかの確認対象としてのみ扱う。
   - `sandbox.filesystem.disabled`（v2.1.216 で追加）: filesystem の隔離のみを解除する
     （network 隔離は維持される）緩和方向の設定であり、本ガイダンスでは**提案しない**。利用者
     環境で既に有効になっていないかの確認対象としてのみ扱う。有効な設定ソースの制限は後述
     「設定したつもり事故」参照。
   - **「設定したつもり事故」**（無言のまま保護が外れる類型。提案時は有効な設定ソース・対象
     バージョン・プラットフォーム・`injectHosts`（`mask` エントリで実値注入を許可する宛先ホスト）
     の有無を必ず添える）:
     - **`filesystem.disabled` 併用時の deny 無効化**（最重要）: `filesystem.disabled` 下では
       `filesystem.denyRead` と `credentials.files` の `deny` 読み取りブロックは無効化される
       （filesystem 層に両方が依存するため）。一方 `credentials.envVars` の `deny`/`mask` と
       `credentials.files` の `mask`（実質的に `deny` として扱われるエントリ＝自動フォールバック分・
       検証時の降格分を除く）は filesystem 層と独立に効く。規則6 は `deny` を提案の主軸に据えるため、`filesystem.disabled` との併用
       提案では files の deny 保護が効かなくなる点を必ず確認する。緩和条件: managed settings が
       `sandbox.filesystem` を設定するか `sandbox.credentials.files` の `deny` エントリを持つ
       場合、`filesystem.disabled` は managed settings からのみ設定可能になる。
     - 設定ソース限定: `strictAllowlist`・`filesystem.disabled`・`credentials` の `mask`
       エントリ・`network.tlsTerminate`・`credentials.allowPlaintextInject` は
       user / managed settings・CLI `--settings` からのみ有効で、`.claude/settings.json`・
       `.claude/settings.local.json`（プロジェクト設定）に書いても効かない（`deny` エントリに
       この制限の記載はない）。
     - 版依存: `mask` の必要バージョンは envVars（v2.1.199 以降）と files（v2.1.221 以降）で
       異なる。不正エントリの扱い（公式ドキュメントの「Invalid entries in managed settings」節）
       も版で変わる: v2.1.191〜v2.1.220 は不正エントリを一律で除去、v2.1.221 以降は `path`/`name`
       が有効な不正エントリのみ `mode: "deny"` へ降格し、`mode` 不明・`path`/`name` 不正のものは
       除去する。除去された場合は保護がまったく効かなくなるため、マスクを設定したつもりで
       無防備になりうる。なおこの寛容な解析は managed settings 限定で、user・project・local
       設定では妥当性検証に失敗したファイルが丸ごと拒否される（無言型ではなく報告はされる）。
     - プラットフォーム差: macOS では files の `mask` は実効ではなく読み取り不可にフォール
       バックする（実値への差し替えは行われない）。
     - `injectHosts` 未指定の既定: 指定を省略すると `network.allowedDomains` の全ホスト宛
       リクエストに実値が注入される（既定が危険側）。`mode: "deny"` エントリでは受理されるが
       無視される。
     - `onExtractNoMatch` の既定 `warn`（`mode: "mask"` かつ `extract` 設定時のみ該当）: 正規
       表現が一致しないとエントリがスキップされ、サンドボックス内から実ファイルが素で読める
       （マスクされない）。
     - `mask` の deny フォールバック: ディレクトリ・glob パターン・8MiB 超・非 UTF-8 な対象は
       `deny` へ自動フォールバックする（マスク前提の運用が静かに崩れる）。
7. ファイルパス系ツールルールのパス glob と hooks の `if:` 条件は、規則1の Bash パターン前方一致とは
   意味論が異なる（確認日 2026-08-04、対象バージョン v2.1.220）。
   - **パターン文法**: `*` は1パスセグメント、`**` は複数セグメントに一致し、末尾 `/**` はそのディレ
     クトリ自身とその配下すべてに一致する。
   - **評価対象の違い**: permissions のパスルールとして評価されるのは `Edit(path)`/`Read(path)` のみ。
     `Write(path)`/`NotebookEdit(path)` 等のパスルールは受理されても参照されない（実装からの警告あり）。
     書き込みを制限したい場合は `Edit(path)` の deny を使う。同様に `Glob(path)` のパスルールも参照
     されず、読み取りを制限したい場合は `Read(path)` の deny を使う（公式ドキュメントの記載に基づく。
     実機確認はしていない）。一方 hooks の `if:` はツール呼び出し時に評価されるため、`Write(pattern)`
     の条件も実際の Write 呼び出しにマッチする（実機確認は Edit・Write。確認日 2026-08-04・
     対象バージョン v2.1.220）。
   - **allow の限定化（v2.1.214 以後）**: 単一セグメント `dir/**`（例: `Edit(src/**)`）は `<cwd>/dir/`
     のみに限定される（それ以前は任意位置の `dir/` への過剰マッチがあり、修正された）。任意の深さに
     一致させるには `**/dir/**` と明示する。
   - **deny/ask の非対称**: deny/ask ルールの単一セグメント `dir/**` は従来どおり任意深度マッチを維持
     する。この非対称の存在自体は実機確認済みの事実だが、その設計意図（allow は狭く・deny は広く、
     安全側に倒す狙い）は公式ドキュメントに明言はなく推測であることに留意する（deny→ask→allow の
     評価順〔規則3〕とは整合する）。この非対称ゆえ、Bash パターンや allow 側で培った一致範囲の直感を
     deny/ask 側の見積もりに持ち込まない・その逆も行わない。
   - **hooks `if:` への影響**: 同じ変更が hooks の `if:` 条件にも及び、既存 hooks 設定が単一セグメント
     `dir/**` を使っている場合は `<cwd>` 起点のみに動作が変わる破壊的変更となる（放置すると意図した
     箇所で発火しなくなる。任意深度が意図なら `if: "Edit(**/dir/**)"` へ書き換える）。allow 側で
     書き換えを怠ると、逆に想定していた自動承認範囲が狭まり承認プロンプトが増える。

## 手順（deny ルール等を提案・変更・レビューする際の確認手順）

1. **一致範囲の確認**: 規則1・2に基づき、提案するパターンが実際にどのコマンド文字列に一致するか
   （意図しない巻き込みの有無）を特定する。
2. **正当なコマンドの列挙**: そのパターンに一致してしまう正当なコマンドを列挙する（規則3）。
3. **利用者側リポジトリの検索**: 利用者側の手順・スクリプト・文書に記載されたコマンドを、提案する
   パターンが止めてしまわないかを検索・確認する（規則3）。
4. **新旧差分の提示**: 既存の permissions を書き換える場合は新旧差分を必ず提示する。既存の書き分けを
   崩す場合は理由を明示する（規則4）。
5. **パターン形の限定**: 提案するパターン形は検証済みの形に限定する。
   - 末尾 `*` の直前にスペースが無い通常形（例: `Bash(git push --force*)`）
   - スペース + `*` 形（例: `Bash(git push --force *)`。引数なし単体形もこの1形でカバーされる）
   - 中間ワイルドカード形（例: `Bash(git -C * push *)`）

   上記いずれにも当たらない未検証の亜種（例: 末尾が `*` を伴わずスペースのみで終わる
   `Bash(git push --force )`）は、動作が未確認のため提案しない。
6. **パス glob の一致範囲確認**: ファイルパス系ツールルール・hooks `if:` 条件でパス glob を
   提案・変更・レビューする場合は、規則7に基づき、提案するパスパターンに実際に一致するパス・
   一致しないパスを具体的に列挙し、単一セグメント（`dir/**`）と `**/` 前置（`**/dir/**`）のどちらを
   意図しているか（`<cwd>` 直下限定か任意深度か）を明示する（手順1のパス版）。あわせて、意図せず
   巻き込んでしまう正当なパスや、意図した対象の漏れがないかを確認し（手順2のパス版）、allow と
   deny/ask で一致範囲が非対称になる点（規則7）を混同していないか確認する。既存 hooks 設定を
   レビューする際は、単一セグメント `dir/**` を用いた `if:` 条件が残っていないかを能動的に検出する。
   v2.1.214 以後は `<cwd>` 起点のみに変わったため、意図していた任意深度の一致が静かに発火しなく
   なっている可能性がある。
7. **許可リスト全体の衛生の確認**: 利用者資材全体のレビュー（`/hw:audit-assets` 等。
   `/hw:optimize-assets` の「動作の阻害」レビューのような単一目的の限定タスクは対象外）または
   許可リストの見直しを目的とする依頼に適用対象を限定し、個別エントリ1件の追加・変更提案では
   下記 (a)〜(c) を省略してよい（削除・縮小を伴う提案は省略の対象外とし、末尾の併用規定に従う）。
   手順1〜6 はエントリ単位の確認であり、これに加え許可リスト全体を次の3点で確認する。
   - (a) **全体像の説明可能性**: `allow`/`ask`/`deny` の各エントリの総数を示し、ワイルドカードを
     含むエントリを列挙する（機微情報〔内部ホスト名・内部パス・認証情報等〕を含む場合はマスク
     するかファイル:行参照に留め、パターン全文は転記しない）。あわせて「このリストは全体として
     何を許可しているか」を1〜2文で説明する。説明できない規模・構成であれば、その事実自体を
     検出事項として報告する。判定は定性的であるため、判定根拠（総数・ワイルドカード件数・
     設定ソース）を必ず添え、可否の断定は利用者に委ねる。
   - (b) **剪定・見直しの契機の有無**: 許可エントリを削除・縮小する運用経路（見直しの契機・
     担当・判断基準）が利用者側の規約に定められているかを確認する。追記のみで削除手段が無い
     場合は、見直し契機の明文化を是正案として提案する。
   - (c) **許可理由の追跡可能性**: 各エントリが「いつ・なぜ許可されたか」を後から再構築できるか
     を確認する。記録が無い場合は `.hw/decisions.md`（機微情報はマスクするかファイル:行参照に
     留める）への判断記録、または利用者側規約文書での理由の明文化を提案する。`.claude/settings.json`
     へのコメント付記は提案しない（標準 JSON であり、コメント許容の記載が公式ドキュメントに
     無い。規則に明記されていない挙動を推測で断定しない方針に従う）。

   (b) の剪定提案、および (a)〜(c) を経ずに提案される削除・縮小提案は、許可を減らす＝作業が
   止まる方向の変更であるため、手順4（新旧差分の提示）および手順1〜3（一致範囲の確認・正当な
   コマンドの列挙・利用者側リポジトリの検索）を必ず併用する。手順3の検索でヒットしないことは
   未使用の証明にはならず、個別エントリの削除を伴う提案では利用者への用途確認を必須とする。

## 注意

- 規則1〜5・7（Bash パターンマッチング・ファイルパス glob・permissions の仕様）は公式ドキュメントの
  確認とローカル実機検証（ヘッドレス `claude -p` 実行）の両方が一致した事実に基づく。規則に明記
  されていないパターンの挙動を推測で断定しない。未確認の挙動が提案に必要な場合は、その旨を明記したうえで
  実機検証を提案するか、確実性より阻止力を優先する代替（hooks・sandbox 設定等の他レイヤー）を
  案内する。
- 規則7 の実機検証範囲は、Edit/Read の permissions パスルール（allow の `<cwd>` 限定・deny/ask の
  任意深度維持〔ask はネストされたパスでの確認〕）、Write ルールが permissions のパスルールとして
  参照されないこと、および hooks の `if:` 条件（PreToolUse の Edit・Write ツール呼び出しで実機確認
  済み。単一セグメントの `<cwd>` 限定は Write でも同じであることを確認）に及ぶ。Bash・Cd・
  PostToolUse 等の他ツール・他フックイベントでの挙動は公式ドキュメントの記載に基づく推定であり、
  実機検証はしていない。規則7内の `Glob(path)` に関する記載（`Read(path)` の deny で代替する旨）も
  公式ドキュメントの記載のみに基づき、実機検証はしていない（規則7本文に明記済み）。
- 規則6（sandbox 設定・credentials 設定を含む）は公式ドキュメントの確認のみに基づき、ローカルでの実機検証は行っていない
  （検証環境を用意できなかったため）。挙動を公式ドキュメントの記載を超えて断定せず、確実性が
  必要な場面では利用者側での事前確認を促す。
- 引数を制約する Bash パターンによる deny は回避されうる（規則5）。確実な阻止が求められる場面
  （リリース保護等）では、Bash パターンのみに頼らず hooks・sandbox 設定（規則6）・ツール単位の
  deny（例: `WebFetch(domain:…)` への寄せ）等の多層防御を提案に含める。
