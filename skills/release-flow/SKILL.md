# リリース標準手順

対象プロジェクトのリリースを安全に実施するための標準フロー。判定は /hw:release コマンドでも実施できる。

## 手順

各ステップに実行主体を付記する（担当エージェント名、または「呼び出し元が直接実行する」＝この
スキルを使っているエージェント自身が判断を挟まず直接行う、のいずれか）。判断を伴わない機械的な
手順はスクリプト化を優先する。

1. **対象と範囲の確定**（実行主体: mgmt-release。対象・範囲の確定は判断を伴うため）
   - 対象プロジェクトとリリースバージョンを確定する（バージョニング規則は既存のタグ・changelog に合わせる）
   - 前回リリース以降の変更一覧を作成する（判断を伴わない機械的作業。実行主体: 呼び出し元が直接実行する。
     `bash scripts/git-changelog.sh <前回リリースのタグ等>` で git 履歴から Conventional Commits の
     種別ごとに整形した一覧を取得できる。使い方は `scripts/git-changelog.sh` 冒頭のコメントを参照）
   - 他サービスへの影響（API 契約の変更・共有ライブラリの更新・DB マイグレーション）を洗い出す（判断を伴う。実行主体: mgmt-release が eng-api / eng-db 等の観点を確認しながら判断する）

2. **リリース前チェック**（判断を伴う。実行主体: mgmt-release が各項目の妥当性を判定する。個々の実施自体は該当領域の担当に確認する）
   - [ ] 全テストが成功している（qa-test の観点）
   - [ ] lint / 型チェックが通っている（実行主体: 呼び出し元が直接実行する。CI がある場合はパイプライン経由の結果を確認する）
   - [ ] 重大なセキュリティ検出事項が残っていない（依存パッケージの脆弱性含む。sec-audit の観点）
   - [ ] DB マイグレーションがある場合、適用手順とロールバック手順がある（eng-db の観点）
   - [ ] API の破壊的変更がある場合、依存サービス側の対応が完了している（eng-api の観点）
   - [ ] リリースノート（開発者向け・ユーザー向け）が用意されている（docs-tech / docs-user の観点）

3. **リリース実施**（ユーザーの承認を得てから。判断を伴わない機械的作業。実行主体: いずれも呼び出し元が直接実行する）
   - バージョン番号の更新（該当ファイル: package.json 等、プロジェクトの慣習に従う）
   - changelog / リリースノートの確定
   - タグ付け・リリースブランチ操作（リポジトリの運用ルールに従う）
   - デプロイ（CI/CD がある場合はパイプライン経由を優先する。実行主体: infra-devops が整備したパイプラインを起動する。無ければ呼び出し元が直接実行する）

4. **リリース後**（判断を伴わない機械的作業。実行主体: 呼び出し元が直接実行する。異常が見つかった場合の原因調査は infra-sre / 担当エンジニアに引き継ぐ）
   - 動作確認（ヘルスチェック・主要機能のスモークテスト）
   - 監視の確認（エラー率・レイテンシに異常がないか）
   - 結果を `.hw/reports/release-<日付>-<対象>.md` に記録する

## 注意
- チェックで1つでも重大な問題があれば、リリースを止めて報告する。
- タグ付け・デプロイ等取り消しにくい操作は、必ずユーザーの承認を得てから実施する。
