# 障害対応標準手順

障害報告を受けたときの標準フロー。復旧を最優先し、恒久対応は切り分けて扱う。

利用者側リポジトリに同種の手順資産（`.hw/procedures/`）・業務手順・スキルがあれば、そちらを優先する。本手順は補完・雛形として使う。

## 手順

1. **状況把握（トリアージ）**
   - 事象・影響範囲（どのサービス・どの機能・どの程度のユーザー）・発生時刻を整理する
   - 重要度を判定する: 高（サービス停止・データ破損・セキュリティ侵害）/ 中（主要機能の不具合）/ 低（限定的な不具合）
   - セキュリティ侵害の疑いがある場合は、直ちにその旨を報告し sec-lead の観点で対応方針を立てる

2. **原因調査**
   - ログ・エラーメッセージ・直近の変更（デプロイ・設定変更・依存更新）を確認する
   - 「直近のリリースとの相関」を最初に疑う（あればロールバックが最速の復旧手段）
   - 再現手順を特定する（再現できない場合はその旨を明記）

3. **応急対応（復旧優先）**
   - 選択肢を比較して提示する: ロールバック / 設定変更 / ホットフィックス / 機能の一時停止
   - 本番に影響する操作はユーザーの承認を得てから実施する

4. **ユーザー告知・謝罪文の準備（顧客コミュニケーション）**
   - 重要度に応じて告知の要否を判断する: 高はユーザー向け告知を原則実施、中は影響範囲・問い合わせ状況に応じて判断、低は個別の問い合わせ対応にとどめ告知は行わない
   - 重要度「高」の場合は応急対応と並行して「認知済み・調査中」の一次速報を先に出し、詳細な告知・謝罪文は状況が確定してから本ステップで確定させる
   - 告知が必要な場合は biz-cs が告知文・謝罪文（お詫び告知、個別の問い合わせへの返信を含む）の草案を作成する
   - 原因調査・応急対応の状況を確認し、判明している範囲のみを記載する（未確定の原因・復旧見込みを推測で書かない）

5. **恒久対応**
   - 根本原因を特定し、修正を実装する（担当エンジニアの観点: eng-backend / eng-frontend 等）
   - 再発防止のテストを追加する（qa-test の観点）
   - 検知の改善（監視・アラートの追加）を検討する（infra-sre の観点）

6. **記録（ポストモーテム）**
   - `.hw/reports/incident-<日付>-<件名>.md` に記録する:
     時系列 / 根本原因 / 影響 / 応急対応 / ユーザー告知・謝罪文の内容 / 恒久対応 / 再発防止策
   - 個人やエージェントを責めない書き方にする（非難なきポストモーテム）

## 注意
- 調査より復旧を優先する。ただし原因不明のまま場当たり的な変更を重ねない。
- 対応中の操作はすべて記録に残す。
