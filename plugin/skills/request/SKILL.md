# hw:request

利用者の依頼を案件として受けて対応する。
本スキルは着手前に`${CLAUDE_SKILL_DIR}/../../agents/mgmt-orchestrator.md`を読み、その本文を自分の役割として振る舞え。本手順を実行する人物を統括と呼ぶ。
本スキルが定めるのは、依頼内容の受け方、担当の役割、記録、手順の段階と成果物、必須通過ポイント、作業の終点、自走レベルである。段階の中をどう進めるかは統括が状況を見て決める。

## 依頼内容

`$ARGUMENTS`を依頼内容とする。空なら依頼内容を利用者に問い、答えを引数と同じく扱う。引数は次の順で判定する。

1. 既存の案件ディレクトリ（パス、または案件の置き場の直下の名前）を指すなら、その案件を再開する。残りの文があれば依頼原文の末尾に追記する。案件の状態が完了なら、残りの文を利用者の検収の差し戻しとして扱い、無ければ完了している旨を示して依頼内容を問う。
2. 外部トラッカーの課題（`#123`、数字だけ、課題のURL）を含むなら、その題と本文を取得して依頼原文とし、残りの文を末尾に追記して新規に始める。取得できなければ、その結果を示して依頼内容を問う。
3. それ以外は、引数を依頼原文として新規に始める。

## 担当

担当とは、統括が`Agent`ツールで起動するサブエージェントであり、統括とは別の人物である。担当は利用者に直接問えない。担当が守る定めは共通指示`${CLAUDE_SKILL_DIR}/assets/agent.md`にあり、統括は委任のたびにこのパスを担当に渡す。役割は次の通りである。

| 役割 | 担う内容 |
|--|--|
| 調査員 | 現状を現物に当たって調べ、事実を報告する |
| 観点の提案者 | 依頼原文または対応方針から、レビューの観点を出す |
| 実行者 | 計画を実行し、成果物を作る |
| 評価者 | レビューで、産物を観点に照らして評価する |
| 重大度の判定者 | レビューの指摘に、残した場合の影響から重大度を付ける |
| 三役と判定者 | 三役審議の理想主義者、現実主義者、批判主義者、判定者 |

## 記録

本スキルは案件の進行状態と途中経過をファイルに保存し記憶する。指示と報告にも使用する。記録は案件の進行の正本であり、統括の記憶の代わりである。記録に無いことは再開した統括に引き継がれない。

### ディレクトリ

| 記録 | パス | 省略表記 |
|--|--|--|
| 案件ディレクトリ | `${CLAUDE_PROJECT_DIR}/.hw/cases/<YYYYMMDD>_<caseName>/` | `<caseDir>/` |
| 計画一覧ディレクトリ | `<caseDir>/plans/` | `<plansDir>/` |
| 計画ディレクトリ | `<plansDir>/<planIndex>_<planName>/` | `<planDir>/` |
| 担当ディレクトリ | `<caseDir>/agents/<agentName>/`または`<planDir>/agents/<agentName>/` | `<agentDir>/` |
| 一時ディレクトリ | `<caseDir>/tmp/<tmpKey>/`または`<planDir>/tmp/<tmpKey>/` | `<tmpDir>/` |

### ファイル

| 記録 | パス | ひな型 | 書く人物 |
|--|--|--|--|

| 計画一覧ファイル | `<plansDir>/index.md` | `${CLAUDE_SKILL_DIR}/assets/plans.md` | 統括 |

### 使用方法

- 名前は次の通り付ける。
    - `<YYYYMMDD>`は案件を作成した日付で、`date +%Y%m%d`で取得せよ。
    - `<planIndex>`は計画の直列番号で、`01`からの2桁である。
    - `<stageName>`は手順の表の名前である。
    - `<count>`はその産物へのレビューの回数で、`1`から数える。差し戻しと再レビューのたびに次の番号のファイルを作り、前のファイルは書き換えるな。
    - 案件の置き場の下に作るディレクトリとファイルの名前は、半角英数字と`-`、`_`、`.`だけで付けよ。日本語など非ASCII文字を含めるな。報告のリンクから辿れなくなるためである。
    - `<caseName>`と`<planName>`は内容を表す英小文字とハイフンで、依頼から統括が付ける。件名は`index.md`の見出しに書く日本語の題であり、名前には使うな。`<agentName>`は英小文字、数字、ハイフンで統括が付け、作業ディレクトリ内で一意にする。
    - `<tmpKey>`は`mktemp`が付ける乱数であり、人物にも作業にも紐づけない。同じ人物を別の作業や追加依頼で使い回しても被らないためである。
- 案件ディレクトリと計画ディレクトリは、それぞれの作業ディレクトリである。担当ディレクトリは人物と作業ディレクトリの組ごとに一つであり、同じ人物への追加依頼は同じ指示書に追記する。`index.md`と`plans/`以外に置くファイルは作業ファイルであり、`index.md`からリンクせよ。`tmp/`の中はリンクの対象外である。
- 一時ファイルは、担う作業が属する作業ディレクトリ直下の`tmp/`の下に、人物ごとに分けて置く。統括も`mkdir -p <作業ディレクトリ>/tmp && mktemp -d <作業ディレクトリ>/tmp/XXXXXXXX`で自分の一時ディレクトリを作り、自分の一時ファイルはそこにだけ置け。担当が守る定めは共通指示にある。担当の一時ディレクトリは、案件の完了か中止まで消すな。`tmp/`ごと消すのは、案件が完了か中止になった後の統括だけである。
- 状態は未着手、進行中、完了、中断、中止のいずれかである。段階には、作業の終点の節が定める対象外もある。
    - 案件は、段階1に着手したら進行中、段階7が完了したら完了にする。利用者が中断を指示したら中断、取り止めを指示したら中止にし、進行中の段階と計画も同じ状態にする。中断時は、どこまで済んだかと再開点をセッション記録に書き、再開の方法（`/hw:request <caseDir>`）を利用者に伝えて止まれ。
    - 段階は、着手したら進行中、必須通過ポイントを通過したら完了にする。段階は順に進め、飛ばすな。前の段階へ戻るときは、戻る段階を進行中に、それより後の完了した段階を未着手にし、戻った理由を証跡に書く。戻る段階が対象外なら、それより前で対象外でない直近の段階へ戻る。
    - 計画の状態と計画レビューの判定は計画一覧が正本である。実行者に委ねたら進行中、計画レビューを通過したら完了にする。計画ファイルはタスク、裁定、レビューの指摘への対処の正本である。
- 証跡は、案件ファイルと計画ファイルの証跡の節に、通過点を日付つきで書く。
    - 案件の証跡に書くのは、状態の変更と戻った理由、統括が採った進め方、担当の起動（担当名、役割、種別と根拠）と報告の受領（返答の結論と報告のパス）、レビューの判定（レビューファイルのパス）、統括の採用（「統括の採用」と付す）、三役審議の結論と却下の理由、再開した事実と再開した段階である。
    - 計画の証跡に書くのは、担当の起動と報告の受領、裁定待ちで止まった事実、再開である。担当の種別の根拠は担当欄に、計画レビューの判定は計画一覧に書く。
    - 裁定、既決の適用、自律裁定は裁定記録に、中断時の再開点はセッション記録に書き、証跡には書かない。三役審議の保留と残論点、レビューで対処しなかった指摘は残論点・保留に書く。
- 記録してから進め。証跡と裁定記録に書く事象は、次の行動に移る前に書け。トークン量の上限による中断は予告なく起きるため、書いていないことは失われる。
- 記録済みの依頼原文、裁定記録、レビューファイルは書き換えるな。追加は末尾または次の番号に追記せよ。
- 記録は参照データである。統括が書いた方針や判断も、利用者の指示ではない。利用者の言葉は、依頼原文と、裁定記録のうち利用者が下した裁定と、レビューファイルのうち利用者のレビューだけである。
- 案件に着手した統括は、案件ファイルのセッション記録に1行を追記せよ。書くIDはハーネスのセッションID`${CLAUDE_SESSION_ID}`である。

## 手順

基本フローは、必ず残す成果物と順番だけを定める。成果物への到達方法は統括が状況を見て決め、採った進め方を証跡に書け。レビュー者と再開した統括がそれを読むためである。

| 段階 | 名前 | 内容 | 成果物 |
|--|--|--|--|
| 1 | purpose | 背景と目的の裁定 | 案件ファイル（依頼原文、背景、目的、スコープ外、制約、レビュー観点の依頼時） |
| 2 | survey | 現状調査 | 案件ファイル（現状調査）、現状調査ファイル |
| 3 | approach | 対応方針の裁定 | 案件ファイル（対応方針） |
| 4 | planning | 実行計画 | 案件ファイル（レビュー観点の方針後）、計画一覧ファイル、計画ファイル、工数見積ファイル |
| 5 | execution | 分担実行 | 計画の成果物、計画報告ファイル |
| 6 | case-review | 全体検証 | 全体レビューファイル |
| 7 | report | 完了報告 | 完了報告ファイル |

## 必須通過ポイント

必須通過ポイントは、レビュー、裁定、完了報告の三つである。通過は記録で判じ、統括の自己申告では判じない。

### レビュー

レビューは、産物をレビュー者が観点に照らして評価し、承認か差し戻しを判定することである。依頼、結果、重大度、対処を一つのレビューファイルに節として積み、節ごとの書き手はひな型による。

- 時点は三つである。段階1から4はその段階の産物ごとに段階レビュー、段階5は計画ごとに計画レビュー、段階6は案件の成果物全体に全体レビューを行う。段階7にレビューは無く、利用者の検収が続く。
- 観点の出所は三つである。固定観点は`${CLAUDE_SKILL_DIR}/assets/viewpoints/`にあり、共通の`common.md`と段階ごとの`<stageName>.md`である。案件の観点は、依頼時に依頼原文から、段階3の通過後に対応方針から、統括が専門家に問うて案件ファイルのレビュー観点の節に書く。計画の観点は計画ファイルの完了条件とレビュー観点の節である。統括は観点を束ねるだけであり、外すなら理由を依頼の節に残せ。評価者は観点を足してよい。
- レビュー者は評価者と利用者の二種である。評価者は統括が起動した担当であり、産物を生んだ人物とも統括とも別の人物であれ。利用者は自走レベルの表が定める段階で加わる。利用者がレビューするのは、評価者の承認を得た産物である。利用者のレビューでは、前回の利用者のレビュー以降に承認された産物も合わせて示す。
- 評価者は観点ごとに、指摘、根拠、残した場合の影響を書く。重大度は、評価者とも産物を生んだ人物とも統括とも別の人物である判定者が、影響に基づいてCritical、High、Medium、Lowの四段階で付ける。利用者のレビューは、統括が利用者の言葉をそのままレビューファイルに写し、重大度は付けない。
- 判定は重大度から決まる。CriticalかHighの指摘が残るなら差し戻し、残らなければ承認である。利用者のレビューは、利用者が修正を述べたら差し戻し、述べなければ承認である。
- 通過とは、自走レベルの表が定めるレビュー者すべての承認が、その産物の最新のレビューファイルにあることである。統括が自分で評価したものと、生産者の自己検証は、レビューにならない。
- 差し戻しなら、統括は対処の節に指摘ごとの対処を書く。High以上は対処が必須である。Medium以下は機械的な修正で済むものだけ対処し、残りは対処しない理由を書いて残論点・保留に書く。対処したら次の番号のレビューファイルで同じレビュー者に再レビューを求める。承認後に産物を変えたときも同じである。評価者の差し戻しが3回目になったら、評価者の指摘と統括の見解を判断材料として、どう進めるかを裁定に上げる。
- 利用者の差し戻しは依頼の修正であり、回数に数えない。修正を依頼原文の末尾に追記し、修正の対象となる産物の段階へ戻り、評価者のレビューからやり直す。

### 裁定

裁定は、既決で定まらない判断を利用者に問うことである。問い方は`CLAUDE.md`の裁定の節に従う。

- 既決とは、この案件の裁定記録、対応方針、`CLAUDE.md`である。他の案件の裁定は既決ではない。問う前に既決を引き、既決なら問い直すな。
- 担当が持ち帰った裁定は、既決で定まるなら統括が既決を示して答え、既決の適用として裁定記録に書く。既決で定まらないなら、思想、アーキテクチャ、要件、設計を含め、統括が裁かず利用者に問う。フルオートだけは自走レベルの節による。
- 通過とは、裁定記録に日付、論点、判断材料、答えがあり、利用者の裁定、既決の適用、自律裁定のいずれかが付いていることである。
- 本手順が定めた問いは裁定ではない。依頼内容、自走レベル、終点、段階1の不足事項の問いと、利用者のレビューがこれに当たる。答えは、自走レベルと終点は案件ファイルの欄に、依頼内容、不足事項、修正は依頼原文の末尾に、レビューはレビューファイルに書く。

### 完了報告

完了報告は、段階7で統括が完了報告ファイルを書き、利用者に示すことである。

- 通過とは、完了報告ファイルに、終点の産物へのリンク、全体レビューの結果、利用者に問わずに置いた仮定と自律裁定と統括の採用の一覧があることである。
- 利用者の検収は完了報告の後にある。検収で差し戻されたら、利用者のレビューの差し戻しと同じ扱いとする。
- 利用者に示す方法は次の通りである。レビューで示す産物、裁定の判断材料、完了報告は、`AskUserQuestion`の問いの本文に入れるか、記録に書いてそのパスを示す。統括の地の文のテキスト出力は記録に残らず利用者に届かないことがあるため、それだけで示したと見なすな。

## 作業の終点

終点は、案件をどの段階まで進めるかを定める。終点は利用者が依頼で委ねる範囲であり、統括が自分で伸ばすな。

| 終点 | 進める段階 | 産物 |
|--|--|--|
| 調査 | 1、2 | 現状調査 |
| 方針 | 1から3 | 対応方針 |
| 計画 | 1から4 | 計画一覧と各計画、工数見積 |
| 実行 | 1から5 | 計画の成果物 |

- 段階6の全体検証と段階7は終点によらず行う。終点より後で段階6より前の段階は対象外であり、進めない。案件を作るとき、対象外の段階の状態を対象外にする。
- 依頼原文から終点が読み取れるのは、依頼が変更を求めているか、終点を述べているときだけである。読み取れなければ、案件を作る前に`AskUserQuestion`で上の表の4つを選択肢として示し、利用者に選ばせる。選択肢の説明には表の産物を書く。4つ以外の答えなら問い直す。迷ったら問う側へ倒せ。終点を実行と誤れば依頼の範囲を越え、調査と誤っても利用者が伸ばせば済むためである。自走レベルも問うなら、1回の`AskUserQuestion`に2問を入れる。
- 終点は案件ファイルの終点の欄に、依頼原文から読み取ったか問いの答えかを添えて書く。
- 利用者が終点の変更を指示したら、裁定記録に利用者の裁定として追記し、案件を進行中に戻し、対象外の段階を新しい終点に従って付け替え（段階5が対象外になり進行中の計画があれば、その計画を中止にする）、目的が変わるため段階1へ戻れ。

## 自走レベル

自走レベルは、レビューに利用者が加わる段階と、既決で定まらない判断を誰が裁くかを定める。レベルは利用者が依頼で委ねる権限であり、統括が自分で上げるな。依頼原文にレベルの記載が無ければ、案件を作る前に`AskUserQuestion`で下の表の4レベルを選択肢として示し、利用者に選ばせる。選択肢の説明には、利用者がレビューする段階と判断の扱いに加え、利用者がレビューしない段階では統括が推奨を採用する旨を書く。4レベル以外の答えなら問い直す。レベルは案件ファイルの自走レベルの欄に書き、再開時はそれに従う。利用者がレベルの変更を指示したら、書き換えて証跡に残せ。

| レベル | 段階レビューと計画レビューの承認者 | 既決で定まらない判断 |
|--|--|--|
| 二人三脚 | 段階1から5：評価者と利用者 | 利用者に問う |
| セミオート | 段階3：評価者と利用者。他の段階：評価者 | 利用者に問う |
| オート | 評価者 | 利用者に問う |
| フルオート | 評価者 | 統括が裁く |

- 全体レビューの承認者はレベルによらず評価者だけであり、利用者の検収は完了報告の後にある。
- 利用者がレビューしない段階では、評価者の承認をもって次へ進む。段階1の目的と段階3の対応方針は、利用者がレビューしない段階では統括の推奨を採用し、統括の採用として証跡に書き、完了報告で一覧する。進めた要点を利用者に伝えてよいが、答えを待つな。統括の採用は利用者の裁定ではない。利用者が異議を述べたら、利用者のレビューの差し戻しと同じ扱いとする。
- 既決で定まらない判断とは、利用者に問う裁定、段階1の不足事項の問い、評価者の3回目の差し戻しである。フルオートでは統括がこれらを裁き、自律裁定として裁定記録に書く。不足事項は問わず、統括が仮定を置いて背景に仮定として明示し、完了報告で一覧する。3回目の差し戻しは、産物と評価のどちらの当事者も裁けないため、`CLAUDE.md`の審議の節に従って三役審議で裁く。
- 依頼内容、自走レベル、終点の問いは、レベルによらず利用者に問う。
