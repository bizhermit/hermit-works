# hw:request

依頼元の要望を、引数と対話を通して言語化し、指示書として残す。

言語化とは、依頼元が既に持っている要望を書き出すことであり、実施者が内容を定めることではない。指示書の各節は依頼元の言葉で書き、実施者の解釈・提案・調査結果を加えない。依頼元から引き出せなかった事項は、補わずに未確定事項として残す。

## 入力

- 引数：$ARGUMENTS
- 運用：定められた規則（`CLAUDE.md`、運用手順書等）のうち、外部トラッカーの使用を定めた記述

引数には、要望と、出力先の指定（任意）を併記してよい。

## 指示書

雛形は[templates/instruction.md](${CLAUDE_SKILL_DIR}/templates/instruction.md)である。第1見出しが表題、それ以降が本文である。

- 依頼原文には、引数と、対話における問いと答えを、受けた順にそのまま記す。要約しない。
- 目的、対象と範囲、完了条件、制約の各節は、依頼原文にある語で記す。依頼原文に該当が無く、依頼元が該当なしと答えた節は「なし」と記す。
- 背景は問わない。目的が対話を経て定まった場合に、当初の要望から目的に至った経緯を依頼原文にある語で記す。引数で目的が定まっていれば「なし」と記す。
- 未確定事項には、問うても定まらなかった事項と、依頼元が後で決めるとした事項を記す。

## 手順

1. 引数を読む。引数が無ければ、要望を問う。
2. 引数と答えに、現物を指す語（ファイル、画面、機能、課題番号等）があれば、リポジトリ、または依頼元が示す所在で実在と一意性を確かめる。所在が示されず確かめられないものは、未確定事項に残す。指示対象の特定を超える調査は行わない。
3. 出力先を、出力先の節に従って決める。
4. 引数と答えから指示書の草案全体を手元で組み、指示書全体に対する問題を見つけて依頼元に問う。問いに示すのは問題だけであり、草案は示さない。草案を示すのは手順5である。一度に問う問題は、依頼元が答えられる量に絞る。問題とは、要望から節が定まらない、現物を指す語が見つからないまたは一意でない、依頼原文が互いに矛盾する、出力先の種別は定まるが所在（リポジトリ、プロジェクト、パス等）が定まらない等である。依頼元の答えは複数の節に及び、節は単独では定まらないため、節を一つずつ切り出して問わない。答えを受けたら、依頼原文に追記し、答えが影響するすべての節に反映して草案全体を改め、改めた草案全体について手順2から本手順までを再び行う。問題が無くなるまで繰り返す。
5. 指示書の草案全体と出力先を依頼元に示し、この内容で作成してよいかを問う。承認は指示書全体に対して得る。修正があれば、手順4と同じく影響するすべての節に反映して草案全体を改め、全体を確かめてから再び全体を示す。承認を得るまで出力しない。
6. 出力先へ出力し、作成した課題のURLまたはファイルのパスを報告する。

## 出力先

次の順で決める。上位で定まれば下位は参照しない。

1. 指定：引数または対話で依頼元が示した出力先
2. 運用：定められた規則が外部トラッカーの使用を定めていれば、そのトラッカー
3. 既定：`${CLAUDE_PROJECT_DIR}/.hw/instructions/<YYYYMMDD>_<slug>.md`

いずれの出力先でも内容は同一の指示書であり、表題を課題の題名に、本文を課題の本文に充てる。

外部トラッカーへの課題の作成手順（接続手段、認証、種別やラベル等）は運用が定めるものであり、本スキルは定めない。運用の記述に従い、記述に無い事項は依頼元に問う。

既定のファイルは次のとおり作成する。

- `<YYYYMMDD>`は作成日（`date +%Y%m%d`）
- `<slug>`は表題を表す、ASCIIの小文字とハイフンからなる短い語（例：`login-password-toggle`）。同名のファイルが既にある場合は末尾に`-2`、`-3`と連番を付す
- ディレクトリが無ければ作成し、指示書の全文（表題を含む）をそのまま書き込む

## 停止条件

- 依頼元の答えまたは承認が得られない：問いを示したまま停止する。推測で補って進めない。
- 課題の作成に失敗した：失敗の内容（コマンドと応答）と、指示書の本文をそのまま示して停止する。別の出力先へ独断で出力しない。
