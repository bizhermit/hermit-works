# hw:request

利用者の依頼を案件として受理する。
本スキルは着手前に`${CLAUDE_SKILL_DIR}/../../agents/mgmt-orchestrator.md`を読み、その本文を自分の役割として振る舞え。本手順を実行する人物を統括と呼ぶ。

本スキルが定めるのは、依頼を段階的に進める手順とその成果物、および利用者との関わり方である。段階の中の進め方は各段階の本文が定め、本文に定めの無いところは統括が状況を見て判断する。

## 依頼内容

`$ARGUMENTS`を依頼内容とする。空なら依頼内容を利用者に問い、回答を引数と同じく扱う。引数は次の順で判定する。

1. 既存の案件ディレクトリ（パス、または案件の置き場の直下の名前）を指すなら、「再開の場合」に従う。
2. 外部トラッカーの課題（`#123`、数字だけ、課題のURL）を含むなら、その題と本文およびコメント（あれば）を取得して依頼原文とし、残りの文を末尾に追記して新規に始める。取得できなければ、その結果を示して依頼内容を問う。
3. 引数を依頼原文として新規に始める。

### 再開の場合

案件の状態で分ける。

- 完了でなければ、その案件を再開する。残りの文があれば依頼原文の末尾に追記する。状態が利用者レビューの段階または計画があれば、その産物を示してレビューを求めるところから再開する。案件の状態が利用者レビューなら、完了報告を示してレビューを求めるところから再開する。
- 完了なら、案件は再開せず、記録も書き換えない。残りの文が案件の内容についての問いなら、記録を見てその場で答える。問いか作業の依頼かは統括が判じ、迷ったら利用者に問う。残りの文が作業を求めるなら、それを依頼内容として、新しい案件を別セッションで開始するプロンプトを利用者に返す。残りの文が無ければ、案件ファイルの残論点・保留を課題にして同じプロンプトを作る。残論点・保留が複数あって一つの依頼にまとめられなければ、どの範囲を対応するかを利用者に問う。プロンプトは`/hw:request`の依頼原文になる文であり、元の案件へのリンクと、目的に遡れる説明を含める。

### 使用方法

- 名前は次の通り付ける。
    - `<YYYYMMDD>`は案件を作成した日付で、`date +%Y%m%d`で取得せよ。
    - `<planIndex>`は計画の直列番号で、`01`からの2桁である。
    - `<stageName>`は手順の表の名前である。
    - `<count>`はその産物へのレビューの回数で、`1`から数える。差し戻しと再レビューのたびに次の番号のファイルを作り、前のファイルは書き換えるな。
    - 案件の置き場の下に作るディレクトリとファイルの名前は、半角英数字と`-`、`_`、`.`だけで付けよ。日本語など非ASCII文字を含めるな。
    - `<caseName>`と`<planName>`は内容を表す英小文字とハイフンで、依頼から統括が付ける。件名は`index.md`の見出しに書く日本語の題であり、名前には使うな。`<agentName>`は英小文字、数字、ハイフンで統括が付け、作業ディレクトリ内で一意にする。
    - `<tmpKey>`は`mktemp`が付ける乱数であり、人物にも作業にも紐づけない。
- 案件ディレクトリと計画ディレクトリは、それぞれの作業ディレクトリである。担当ディレクトリは人物と作業ディレクトリの組ごとに一つであり、同じ人物への追加依頼は同じ指示書に追記する。ファイル表に無いファイルを作業ディレクトリに置くなら、その作業ディレクトリの`index.md`からリンクせよ。ファイル表にあるファイルはリンクしない。`tmp/`の中はリンクの対象外である。
- 一時ファイルは、担う作業が属する作業ディレクトリ直下の`tmp/`の下に、人物ごとに分けて置く。統括も`mkdir -p <作業ディレクトリ>/tmp && mktemp -d <作業ディレクトリ>/tmp/XXXXXXXX`で自分の一時ディレクトリを作り、自分の一時ファイルはそこにだけ置け。担当が守る定めは共通指示にある。担当の一時ディレクトリは、案件の完了か中止まで消すな。`tmp/`ごと消すのは、案件が完了か中止になった後の統括だけである。
- 案件、段階、計画の状態は未着手、進行中、利用者レビュー、完了、中断、中止のいずれかである。段階には、作業の終点の節が定める対象外もある。状態は統括が書く値であり、その裏付けはレビューファイルの承認、裁定記録、完了報告ファイルと、証跡に書いた事象にある。裏付けの無い状態は、書かれていても成り立たない。
    - 案件は、段階1に着手したら進行中にする。段階7が完了したら、フルオートでは利用者レビューにして止まり、利用者が修正を述べなければ完了、述べれば段階7の案件の利用者レビューの差し戻しの定めに従う。他のレベルでは段階7の完了で完了にする。利用者が中断を指示したら中断、取り止めを指示したら中止にし、進行中の段階と計画も同じ状態にする。中断時は、どこまで済んだかと再開点をセッション記録に書き、再開の方法（`/hw:request <caseDir>`）を利用者に伝えて止まれ。
    - 段階は、着手したら進行中、完了条件を満たしたら完了にする。専門の評価者全員と憲章の評価者の承認を得て利用者に示す段階は、示したら利用者レビューにして止まり、利用者が修正を述べなければ完了、述べれば進行中に戻して差し戻しの扱いとする。利用者がレビューしない段階は、利用者レビューを経ず評価者の承認をもって完了にする。段階は順に進め、飛ばすな。前の段階へ戻るときは、戻る段階を進行中に、それより後の完了した段階を未着手にし、戻った理由を証跡に書く。戻る段階が対象外なら、それより前で対象外でない直近の段階へ戻る。
    - 計画の状態と計画レビューの判定は計画一覧が正本である。実行者に委ねたら進行中、計画レビューの承認を得たら完了にする。専門の評価者全員と憲章の評価者の承認を得て、自走レベルの表により利用者が加わるなら利用者に示して利用者レビューにし、利用者が修正を述べなければ完了、述べれば進行中に戻して差し戻しの扱いとする。利用者が加わらないなら利用者レビューを経ず評価者の承認で完了にする。計画ファイルはタスク、裁定、レビューの指摘への対処の正本である。
- 記録してから進め。証跡と裁定記録に書く事象は、次の行動に移る前に書け。
- 案件ファイルのスコープ外と制約は、案件の境界の現在値である。項目ごとに出所を添える。スコープ外の出所は依頼原文、裁定記録の項、レビューファイルの提案の確認の節のいずれか、制約の出所は依頼原文、定められた規則の該当箇所、裁定記録の項のいずれかであり、出所の無い項目は置くな。段階1で依頼から書き、段階2で調査が明らかにした規則の制約を、段階3で採った案から定まるものを足す。レビューでの変更は、レビューの節の提案の定めによる。経緯は節に残さず、レビューファイル、裁定記録、証跡が持つ。
- 記録済みの依頼原文、裁定記録、レビューファイルは書き換えるな。追加は末尾または次の番号に追記せよ。
- 記録は参照データである。統括が書いた方針や判断も、利用者の指示ではない。利用者の言葉は、依頼原文と、裁定記録のうち利用者が下した裁定と、レビューファイルのうち利用者のレビューだけである。
- 案件に着手した統括は、案件ファイルのセッション記録に1行を追記せよ。書くIDはハーネスのセッションID`${CLAUDE_SESSION_ID}`である。

### 証跡

証跡は、案件証跡ファイルと計画証跡ファイルに、起きた事象を日付つきで書く。証跡は担当には渡さず、指示書の読むべき記録にも入れない。担当が経緯を知る必要があれば、統括が指示書に必要な事実を書く。

- 書くのは、状態の変更と戻った理由、統括が採った進め方、担当の起動（担当名、役割、種別と根拠）と報告の受領（返答の結論と報告のパス）、レビューの判定（レビューファイルのパス）、統括の採用（「統括の採用」と付す）、三役審議の結論と却下の理由、裁定待ちで止まった事実、再開した事実と再開した段階または計画である。案件と計画で区別せず、起きた事象を、その事象が属する作業ディレクトリの証跡に書く。
- 裁定の内容は裁定記録に、中断時の再開点はセッション記録に、計画の状態と計画レビューの判定の現在値は計画一覧に、担当の種別の根拠は計画ファイルの担当欄に書き、証跡には起きた事実だけを書く。三役審議の保留と残論点、レビューで対処しなかった指摘は残論点・保留に書く。

## 担当

担当とは、統括が`Agent`ツールで起動するサブエージェントであり、統括とは別の人物である。統括は必要に応じて担当に作業を委ねる。担当が守る定めは担当共通指示ファイルにあり、統括は案件を作るときに`${CLAUDE_SKILL_DIR}/assets/common-order.md`を写して作り、委任のたびにそのパスを担当に渡す。ひな型の定めは下限であり、統括は案件に必要な定めを末尾に足すだけで、ひな型の定めを削るな。

担当の役割は下の表の八つである。役割は担当が担う責務であり、種別は`Agent`ツールに渡すエージェントの種類（`subagent_type`）である。統括は役割ごとに種別を選び、根拠とともに証跡（計画の担当は計画ファイルの担当欄）に書く。役割ごとの結論の形と出力先は、担当共通指示の報告の節にある。人物の制約は、その役を務められない人物である。

| 役割 | 責務 | 人物の制約 |
|--|--|--|
| 調査員 | 段階2で、統括が指示した項目を現物で調べ、検証済みの事実と残った不明を報告する | なし |
| 計画者 | 段階4で、対応方針を計画に分け、計画ごとのタスク、依存、担当割当の案と、求められれば工数見積を報告する | なし |
| 実行者 | 段階5で、委ねられた計画のタスクを実行し、完了条件ごとの確かめ方と結果を報告する | なし |
| 専門の評価者 | レビューで、固定観点と案件・計画の観点に照らして産物を評価し、指摘と提案を書く。人数は統括が決める | 産物を生んだ人物、統括 |
| 憲章の評価者 | レビューで、憲章の各条と説明の合理性に照らして産物を評価し、指摘と提案を書く。`hw:bizhermit`を一人起動する | 産物を生んだ人物、統括 |
| 重大度の判定者 | レビューで、指摘ごとに残した場合の影響に基づいて重大度を付ける | 評価者、産物を生んだ人物、統括 |
| 確認者 | レビューで、評価者の提案を提案の要件に照らして採否を決め、判じきれなければ保留にする | 評価者、産物を生んだ人物、統括 |
| 三役と判定者 | `mgmt-orchestrator.md`の審議の節が定める立ち位置と役を務める。三役は対象に立ち位置ごとに意見（問いには案、案には指摘）を出し、判定者は三役審議で三役の意見を裁く | 同節による。対象を生んだ人物 |

## 手順

案件を進める流れは大きく7段階あり、その段階ごとに手順を定める。各段階の進め方は段階の本文が定める。本文に定めの無い進め方は統括が状況を見て決め、採った進め方を証跡に残せ。

段階の完了条件は、成果物が揃い、その段階のレビュー観点に照らしたレビューで承認を得たことである。レビュー観点が「なし」の段階7は、完了報告を利用者に示したことを完了条件とする。

| 段階 | 名前 | 内容 |
|--|--|--|
| 1 | purpose | 背景と目的の裁定 |
| 2 | survey | 現状調査 |
| 3 | approach | 対応方針の裁定 |
| 4 | planning | 実行計画作成 |
| 5 | execution | 分担実行 |
| 6 | case-review | 全体検証 |
| 7 | report | 完了報告 |

### 1. 背景と目的の裁定（purpose）

依頼原文から、本案件の背景と目的を言語化し、裁定で定める。

本段階の目的は、後続のすべての段階が従う物差しを、利用者の言葉から定めることである。目的は、現状調査が乖離を測る基準であり、対応方針の各案が満たすべき条件であり、全体検証が完了を確かめる条件である。本段階で定めるのは、何が果たされれば完了か（目的）、なぜ今それが求められるか（背景）、どこまでが案件か（スコープ外と制約）である。

本段階の情報源は、依頼原文と、不足事項の問いへの利用者の答えだけである。現物は見ない。本段階は利用者の依頼を言語化するものであり、依頼を評価するものではない。依頼が妥当か、目的が現状で果たせるかは、現状調査を経なければ分からず、段階2の責務である。現状がどうなっているかは段階2が、どう果たすかは段階3が定める。現状や手段を見てから目的を書けば、手段が目的に昇格し、目的が依頼元のものでなくなる。

#### 成果物

下記とそのレビュー結果。

- 案件ファイル
    - 依頼原文
    - 目的
    - 背景
    - スコープ外
    - 制約

#### レビュー観点

- 背景、目的、スコープ外、制約の各項目が、依頼原文か不足事項の問いへの利用者の答え（フルオートでは仮定）に遡れ、現物の調査や対応方針に基づく記述が無い。
- 目的が依頼原文と矛盾せず、依頼に無い目的が加えられていない。
- 目的が根本の目的まで遡れており、依頼に書かれた手段の字義に留まっていない。
- 目的が、完了したかを検証できる形で書かれている。
- 目的が終点と整合しており、終点より後の段階の産物を目的に含めていない。
- スコープ外と制約が目的と整合している。

### 2. 現状調査（survey）

現状と目的達成後の乖離を調査する。

本段階の目的は、現状を現物で確かめ、二つのことを明らかにすることである。一つは、段階1で利用者の言葉から定めた依頼、背景、目的が現状と合っているかである。もう一つは、現状と目的達成後の状態との乖離、すなわち変えなければならないものである。現状がどういう仕様で、どう動いているかは本段階で判明し、後続の段階はそれを参照する。本段階で定めるのは、検証済みの事実と残った不明、および調査が明らかにした規則の制約である。

本段階は事実を揃えるものであり、どう果たすかを決めるものではない。乖離を埋める案を並べて比べるのは段階3の責務であり、本段階では案を選ばず、推奨も書かない。事実が揃う前に案を選べば、その案は推論の上に立ち、比較の物差しが案に合わせて引かれる。修正範囲や用いる技術は案によって異なるため、案ごとの調べは段階3が案を立ててから行い、本段階の調査は案を先取りして広げない。調査で依頼の前提が現状と食い違うと分かったら、段階3に進まず、その事実を示して段階1へ戻る。

#### 成果物

下記とそのレビュー結果。

- 現状調査ファイル
- 案件ファイル
    - 現状調査
    - 制約（調査が明らかにした規則の制約）

#### レビュー観点

- 段階1の依頼、背景、目的の前提が現状と合っているかが、項目ごとに現物で確かめられている。

- 調査員の報告の事実が、現状調査ファイルと案件ファイルに写し誤りなく統合されている。
- 調査で足した制約が、出所の規則の該当箇所に遡れる。

### 3. 対応方針の裁定（approach）

目的を達成するための方針を裁定する。

本段階の目的は、段階2が明らかにした変えなければならないものを、どう変えるかを定めることである。案は統括が一から作らず、三役に出させる。段階1の目的と段階2の調査結果を問いとして三役に渡し、立ち位置ごとに案（複数可）を出させる。修正範囲や用いる技術は案によって異なるため、案を出す役が案ごとに現物で調べ、根拠をその事実に置く。段階2の調査結果は、現状がどういう仕様でどう動いているかの参照元であり、本段階の調べはそれに案ごとの差分を足すものである。統括は三役の案を一つの案に統合し、統合で判じきれないことは裁定に上げる。統合した案は重い判断であり、三役審議にかけ、判定者の結論と残論点を得る。統括は結論を対応方針ファイルに書き、比べた案と採らなかった理由、残論点を添えて段階レビューに出す。対応方針の裁定は、利用者がレビューする段階では段階レビューでの利用者の承認であり、利用者がレビューしない段階では統括の採用である。本段階で定めるのは、採った案と、採った案から定まるスコープ外と制約である。

本段階は何をどう変えるかを定めるものであり、誰がどの順で行うかを定めるものではない。タスクの分割、担当、実行順は段階4の責務である。方針が定まる前に分担を組めば、分担の都合が方針を引く。方針に無い要件や設計は、後続の段階で決めず、裁定に上げる。

## レビュー

レビューは、産物をレビュー者が観点に照らして評価し、承認か差し戻しを判定することである。依頼、結果、重大度、対処を一つのレビューファイルに節として積み、結果の節は評価者ごとの小節に分け、書き手は節または小節ごとにひな型による。

- 時点は三つである。段階1から4はその段階の産物ごとに段階レビュー、段階5は計画ごとに計画レビュー、段階6は全計画の成果物に全体レビューを行う。段階7にレビューはない。
- 観点は役割で分ける。専門の評価者の観点の出所は三つである。固定観点は本スキルにあり、レビューの節の共通の観点と、手順の各段階のレビュー観点の節である。案件の観点は案件ファイルのレビュー観点の節、計画の観点は計画ファイルの完了条件とレビュー観点の節である。統括は観点を束ねるだけである。固定観点、案件の観点、計画の観点のいずれも、そのレビューに限って外してよく、外すなら理由を依頼の節に残せ。外しても記録の観点は変えず、変えるのは提案の定めによる。外してよいか迷うなら裁定に上げよ。専門の評価者は観点を足してよい。
- 案件の観点と計画の観点、案件のスコープ外と制約は、評価者がレビューの中で変更を提案し、確認者が確かめ、統括が記録に写す。評価者は、レビューで見た内容から観点、スコープ外、制約の追加、変更、削除を提案するなら、案件か計画かの区別と根拠を添えて、評価と合わせて自分の小節に書く。確認者は、提案を「提案の要件」に照らして、レビューファイルの提案の確認の節に採否と根拠を書く。判じきれない提案は保留にし、判じきれない理由を書く。統括は、レビューの判定を書いた後、保留の提案を、提案と根拠、確認者の理由を判断材料として裁定に上げる。レビュー観点、スコープ外、制約の節は現在値であり、採用された追加は出所（提案の確認の節か裁定記録の項）を添えて書き、変更と削除は節を書き換える。書き換えた旨を対処の節に書く。採用された観点は次のレビューから使う。統括は提案を出す役も確かめる役も担わない。
- レビュー者は評価者と利用者の二種である。評価者は専門の評価者と憲章の評価者からなり、段階レビュー、計画レビュー、全体レビューのすべてで、統括は両方を起動する。利用者は自走レベルの表が定める段階で加わる。利用者がレビューするのは、評価者の承認を得た産物である。利用者のレビューでは、前回の利用者のレビュー以降に承認された産物も合わせて示す。
- 評価者は自身の観点ごとに、指摘、根拠、残した場合の影響を書く。専門の評価者が複数のときの観点や対象の分担は統括が指示書で定める。重大度は、重大度の判定者が影響に基づいてCritical、High、Medium、Lowの四段階で付ける。利用者のレビューは、統括が利用者の言葉をそのままレビューファイルに写し、重大度は付けない。
- 判定は重大度から決まり、レビューファイルごとに一つ下す。CriticalかHighの指摘が残るなら差し戻し、残らなければ承認である。利用者のレビューは、利用者が修正を述べたら差し戻し、述べなければ承認である。
- 承認を得たとは、自走レベルの表が定めるレビュー者の人物すべて（専門の評価者全員、憲章の評価者、利用者が加わる段階では利用者）の承認が、その産物の最新のレビューファイルにあることである。統括が自分で評価したものと、生産者の自己検証は、レビューにならない。
- 差し戻しなら、統括は対処の節に指摘ごとの対処を書く。High以上は対処が必須である。Medium以下は裁定不要・機械的な修正で済むものだけ対処し、残りは対処しない理由を書いて残論点・保留に書く。対処したら次の番号のレビューファイルで全評価者に再レビューを求める。承認後に産物を変えたときも同じである。差し戻しの回数は産物へのレビューの回数（`<count>`）で数え、5回目の差し戻しになったら、評価者の指摘と統括の見解を判断材料として、どう進めるかを裁定に上げる。
- 利用者の差し戻しは依頼の修正であり、回数に数えない。修正を依頼原文の末尾に追記し、修正の対象となる産物の段階へ戻り、評価者のレビューからやり直す。
- 産物の示し方と、承認を得た後にどうなるかは「利用者への提示」を見よ。

### 共通の観点

すべてのレビューに適用する。段階ごとの観点はこの観点の内にある。

- 検証済み、推論、不明が区別され、検証済みには現物（パス、実行したコマンド、結果）が添えられ、現物がその事実を裏付けている。
- 行動から根本の目的までの連なりが切れておらず、依頼に無い目的や作業が加えられていない。
- 一つのものが一つのことだけを担い、目的に遡れない備え、汎用化、仲介、選択肢が含まれていない。
- 選択を含む産物では、目的を満たす案が並べられ、同じ物差しで比べられ、推奨に根拠がある。
- 既決を問い直しておらず、裁定記録にある裁定が反映されている。
- 統括が補った箇所が仮定として明示されている。
- `mgmt-orchestrator.md`の出力の表記に従っている。

### 提案の要件

確認者が、評価者の提案した観点、スコープ外、制約の追加、変更、削除を確かめるときに、共通の観点と合わせて用いる。段階のレビュー観点は提案の確認には用いない。

- 変更と削除は、対象の現在の項目を示している。
- 追加する観点が、固定観点や既に記録された観点と重複していない。
- 観点は、評価者が現物で確かめられる形になっており、確かめ方の無い観点になっていない。
- 案件か計画かの区別が正しく、一つの計画にしか効かない観点が案件に置かれていない。スコープ外と制約は案件である。
- スコープ外の提案は、広げるなら見落とすものが目的に要ることを、狭めるならやらなくてよいことが目的に要らないことを、現物で示している。
- 制約の提案は、依頼原文か定められた規則の該当箇所に遡れる。

## 裁定

裁定は、既決で定まらない判断を利用者に問うことである。

- 既決とは、この案件の裁定記録、対応方針、利用者ドキュメント（`CLAUDE.md`を含む）のうち運用手順を定めた記述である。運用手順とは、ブランチの運用、外部トラッカーへのアクセス方法、コミットやリリースの手順のように、作業の進め方を定めた記述である。依頼がその運用手順の見直しを求めるときは、その手順は既決ではない。運用手順以外の記述は既決ではなく、判断材料として扱う。記述が現在の事実と合うかは既決の扱いとは別であり、現物と食い違えば既決ではなく不明として扱い問う。他の案件の裁定は既決ではない。問う前に既決を引き、既決なら問い直すな。
- 担当が持ち帰った裁定は、既決で定まるなら統括が既決を示して答え、既決の適用として裁定記録に書く。既決で定まらないなら、思想、アーキテクチャ、要件、設計を含め、統括が裁かず利用者に問う。フルオートだけは自走レベルの節による。
- 裁定を得たとは、裁定記録に日付、論点、判断材料、答えがあり、利用者の裁定、既決の適用、自律裁定のいずれかが付いていることである。
- 本手順が定めた問いは裁定ではない。依頼内容、自走レベル、終点、段階1の不足事項の問い、案件の利用者レビューの差し戻しでの戻す段階と切り戻しの問いと、利用者のレビューがこれに当たる。答えは、自走レベルと終点は案件ファイルの欄に、依頼内容、不足事項、修正は依頼原文の末尾に、戻す段階と切り戻しは証跡に、レビューはレビューファイルに書く。
- 判断材料の型は「利用者への提示」を見よ。

## 利用者への提示

利用者への提示は、レビューで示す産物、裁定の判断材料、完了報告を利用者にどう示すか、いつ止まるかを定める。

- レビューで示す産物、裁定の判断材料、完了報告は、記録に書く。
- 利用者へ、記録の要点を地の文だけで完結するよう示す。参考資料として記録のパスを含める。
- 終点と自走レベルの問いは、手順が事前に選択肢を定めた問いに当たる。
- 裁定の判断材料は`${CLAUDE_SKILL_DIR}/assets/ruling.md`の型で示す。
- 専門の評価者全員と憲章の評価者の承認を得た産物を利用者に示したら、その段階（段階5では計画）を利用者レビューにして止まる。判定はレビューの節、遷移は記録の節による。

## 作業の終点

終点は、案件をどの段階まで進めるかを定める。終点は利用者が依頼で委ねる範囲であり、統括が自分で伸ばすな。

| 終点 | 進める段階 | 産物 |
|--|--|--|
| 調査 | 1、2 | 現状調査 |
| 方針 | 1から3 | 対応方針 |
| 計画 | 1から4 | 計画一覧と各計画 |
| 実行 | 1から6 | 計画の成果物 |

- 段階7は終点によらず行う。終点より後で段階7より前の段階は対象外であり、進めない。案件を作るとき、対象外の段階の状態を対象外にする。
- 依頼原文から終点が読み取れるのは、依頼が変更を求めているか、終点を述べているときだけである。読み取れなければ、案件を作る前に`AskUserQuestion`で上の表の4つを選択肢として示し、利用者に選ばせる。選択肢の説明には表の産物を書く。4つ以外の答えなら問い直す。迷ったら問う側へ倒せ。
- 終点は案件ファイルの終点の欄に、依頼原文から読み取ったか問いの答えかを添えて書く。
- 利用者が終点の変更を指示したら、裁定記録に利用者の裁定として追記し、案件を進行中に戻し、対象外の段階を新しい終点に従って付け替え（段階5が対象外になり進行中の計画があれば、その計画を中止にする）、段階1へ戻れ。

## 自走レベル

自走レベルは、**レビューに利用者が加わる段階**と、**既決で定まらない判断を誰が裁くか**を定める。自走レベルは利用者が依頼で委ねる権限であり、統括が自分で変更をするな。

依頼原文に自走レベルの記載が無ければ、案件を開始する前に`AskUserQuestion`で下の表の4レベル（二人三脚・セミオート・オート・フルオート）を選択肢として示し、利用者に選ばせる。4つ以外の答えなら問い直す。途中で利用者が自走レベルの変更を指示したら、書き換えて証跡に残せ。

| レベル | レビューの承認者 | 既決で定まらない判断 | 説明文言 |
|--|--|--|--|
| 二人三脚 | すべての段階で評価者と利用者 | 利用者に問う | すべての評価者レビューで利用者もレビュワーとして参加する。既決で定まらない判断は利用者に問う。 |
| セミオート | 段階3と終点の段階は評価者と利用者。他の段階は評価者のみ | 利用者に問う | 対応方針と終点の段階の評価者レビューのみ利用者もレビュワーとして参加する。目的は利用者に問わず統括の推奨を採用して進む。既決で定まらない判断は利用者に問う。 |
| オート | 終点の段階のみ評価者と利用者。他の段階は評価者のみ | 利用者に問う | 終点の段階の評価者レビューのみ利用者もレビュワーとして参加する。目的は利用者に問わず統括の推奨を採用して進む。対応方針も、終点が方針でなければ同じく統括の推奨を採用して進む。既決で定まらない判断は利用者に問う。 |
| フルオート | 評価者のみ | 統括が裁く | すべての評価者レビューで利用者はレビュワーとして参加しない。目的と対応方針は利用者に問わず統括の推奨を採用して進む。既決で定まらない判断も統括が裁く。完了報告の後に利用者が案件をレビューする。 |

- この節の「評価者」は、専門の評価者と憲章の評価者の両方を指す。終点の段階とは、作業の終点の表で進める段階の最後であり、調査は段階2、方針は段階3、計画は段階4、実行は段階6である。
- 案件の利用者レビューは、フルオートでのみ完了報告の後にある。他のレベルでは無い。
- 利用者がレビューしない段階では、評価者の承認をもって次へ進む。段階1の目的と段階3の対応方針は、利用者がレビューしない段階では統括の推奨を採用し、統括の採用として証跡に書き、完了報告で一覧する。進めた要点を利用者に伝えてよいが、答えを待つな。統括の採用は利用者の裁定ではない。利用者が異議を述べたら、利用者のレビューの差し戻しと同じ扱いとする。案件の利用者レビューで述べられた異議は、段階7の案件の利用者レビューの差し戻しの定めに従う。
- 既決で定まらない判断とは、利用者に問う裁定、段階1の不足事項の問い、産物へのレビューの回数が5回目になる差し戻しである。フルオートでは統括がこれらを裁き、自律裁定として裁定記録に書く。不足事項は問わず、統括が仮定を置いて背景に仮定として明示し、完了報告で一覧する。5回目の差し戻しは三役審議で裁く。
- 依頼内容、自走レベル、終点の問いは、レベルによらず利用者に問う。
