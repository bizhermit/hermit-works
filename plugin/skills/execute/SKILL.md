# hw:execute

指示書を受け、実行計画を立て、計画のタスクごとに実行者に実施させ、評価者のレビューを経て成果物を仕上げる。本スキルを実施する人物を統括と呼ぶ。統括は計画、担当の起動、判定、依頼元との対話を担い、成果物を自分では作らない。

## 入力

- 引数：$ARGUMENTS
- 指示書：`hw:request`が作成した指示書。引数が示すファイル、または運用で定められた外部トラッカーの課題
- 運用：定められた規則（`CLAUDE.md`、運用手順書等）のうち、外部トラッカーの使用を定めた記述

引数が無ければ、`${CLAUDE_PROJECT_DIR}/.hw/instructions/`にある指示書を一覧し、どれを実行するかを問う。引数がファイルのパスでなければ、運用の記述に従って課題の本文を取得する。運用に取得の手順が無ければ問う。

## 役割

- 統括：本スキルを実施する人物。計画を立て、担当を起動し、判定し、依頼元と対話する
- 実行者：`hw:worker`。計画の一つのタスクを行い、報告を返す
- 評価者：`hw:reviewer`。一つのタスクまたは案件全体の成果物を、完了条件、制約、境界に照らして現物で確かめ、レビューを返す。成果物を変更しない

実行者と評価者は起動のたびに新しい人物であり、前回の担当の記憶を持たない。前回の内容は記録（報告、レビュー）で渡す。実行した人物と確かめる人物は常に別である。

## 作業ディレクトリ

案件ごとに`${CLAUDE_PROJECT_DIR}/.hw/cases/<YYYYMMDD>_<slug>/`を作る。`<YYYYMMDD>`は着手日（`date +%Y%m%d`）、`<slug>`は指示書の表題を表すASCIIの小文字とハイフンからなる短い語である。同名のディレクトリが既にある場合は末尾に`-2`、`-3`と連番を付す。

```text
<案件ディレクトリ>/
├── instruction.md        # 指示書の写し
├── plan.md               # 実行計画と経過。雛形はtemplates/plan.md
├── reviewer-<n>.md       # 全体レビュー。雛形はtemplates/review.md
├── tmp/reviewer-<n>/     # 全体レビューの評価者の一時ファイル
└── tasks/<NN>_<slug>/    # タスクごとの記録
    ├── worker-<n>.md     # 実行者の報告。雛形はtemplates/report.md
    ├── reviewer-<n>.md   # 評価者のレビュー。雛形はtemplates/review.md
    └── tmp/              # 一時ファイル。実行者はworker-<n>/、評価者はreviewer-<n>/
```

`<NN>`はタスクの番号（`01`から）、`<n>`は回数（`1`から）である。記録の名前は書いた役割を表す。実行者を起動するたびに報告の回数が進み、評価者を起動するたびにレビューの回数が進む。統括が行ったこと（問いと答え、承認、担当の起動、報告の受領、判定、状態の変更）は、その都度`plan.md`の経過の節に日時（`YYYY-MM-DD HH:MM:SS`）を付けて記す。

## 手順

### 1. 指示書を読む

指示書を読み、案件ディレクトリを作り、`instruction.md`に全文を写す。指示書に現物を指す語（ファイル、画面、機能等）があれば、リポジトリ、または指示書が示す所在で実在を確かめる。確かめられないものは未確定事項として扱う。指示書に目的または完了条件が無ければ、計画を立てられないため、`hw:request`で補うよう示して停止する。

### 2. 未確定事項を解く

指示書の未確定事項と、計画を立てるうえで指示書から定まらない事項を、一件ずつ依頼元に問う。答えは`plan.md`の裁定の節に記す。依頼元が後で決めるとした事項があれば、その事項に依らないタスクだけを計画し、依る部分は残論点として`plan.md`に書く。

### 3. 計画を立てる

[templates/plan.md](${CLAUDE_SKILL_DIR}/templates/plan.md)に従って`plan.md`を書く。

- 目的、完了条件、制約と境界は指示書の語で写し、統括が具体化した部分（確かめ方、パス）を書き足す。指示書に無い要件を加えない
- タスクは、成果物と完了条件が一つに定まる単位に分ける。一つのタスクが担うことは一つにする
- タスクごとに、行うこと、成果物、完了条件と確かめ方、触ってよい範囲、依存を書く
- 完了条件は現物で確かめられる形（実行するコマンド、比べる対象、見る画面）で書く
- 指示書の完了条件のすべてが、いずれかのタスクの完了条件または全体レビューで確かめられることを確かめる。確かめられない条件があれば、依頼元に示して言い直しを問う

### 4. 承認を得る

`plan.md`の全文を依頼元に示し、この計画で実行してよいかを問う。修正があれば反映して再び示す。承認を得るまで実行に進まない。承認後に計画を変える（タスクの追加、削除、完了条件や範囲の変更）ときも同じく承認を得る。

### 5. タスクを実行する

依存の順にタスクを進める。互いに依存せず、触ってよい範囲が重ならないタスクは同時に進めてよい。タスクごとに次を繰り返す。

1. 実行者を起動する
2. 返答の結論を見る。判断待ちなら、報告の判断を求める事項の節を読み、依頼元に一件ずつ問い、答えを裁定の節に記して、実行者を再び起動する。中断なら、報告の全文を読み、内容を依頼元に示して判断を問う
3. 結論が完了なら、評価者を起動する
4. 判定が承認なら、レビューを読まずに採り、タスクの状態を完了にして次へ進む
5. 判定が差し戻しなら、レビューの指摘の節を読んで対応を決め、実行者を再び起動する。同じタスクの差し戻しが3回に達したら繰り返さず、レビューの指摘と経過を依頼元に示して判断を問う

統括が記録を読むのは、手順の各段が定める節だけである。節は見出しで抜き出して読む。抜き出した結果が空なら、記録の全文を読む。統括は成果物を自分で直さない。

### 6. 全体レビュー

すべてのタスクが完了したら評価者を起動し、指示書の完了条件のすべてを成果物に照らして確かめさせる。判定が差し戻しなら、全体レビューの指摘の節を読み、指摘が指すタスクを差し戻す。該当するタスクが無ければ、タスクを追加して承認を得る。判定が承認なら、指示書が求めているコミット等の後処理を行い、案件の状態を完了にして完了日時を記す。

### 7. 報告する

全体レビューの完了条件の検証の節と、提案が1件以上あるレビューの提案の節と、各タスクの最新の報告の気づいたことの節を読む。`plan.md`の結果の節に、完了条件ごとの検証結果、成果物の一覧、残論点、全体レビューへのリンクを書く。依頼元には、結論、成果物の一覧、完了条件の検証結果、残論点、評価者の提案、実行者の気づいたこと、案件ディレクトリのパスを報告する。提案と気づいたことを採るかは依頼元が決める。

## 担当の起動

担当は`Agent`ツールで起動する。`subagent_type`は実行者が`hw:worker`、評価者が`hw:reviewer`である。担当は呼び出し元を限らない汎用の人物であり、計画も案件も知らない。作業に要るものは`plan.md`から取り出してプロンプトに書き、`plan.md`と案件ディレクトリの構成は渡さない。

- 実行者に渡す
    - 作業：該当タスクの行うことと成果物
    - 目的：指示書の目的
    - 完了条件：該当タスクの完了条件と確かめ方
    - 制約：指示書の制約と、コミット、プッシュ、PRの作成を行わないこと
    - 変えてよい範囲：該当タスクの触ってよい範囲
    - 一時領域：`tasks/<NN>_<slug>/tmp/worker-<n>/`
    - 読む資料：依存するタスクの成果物と最新の報告のパス。差し戻しであれば前回の報告のパス
    - 指摘：差し戻しであれば前回のレビューのパスと、その指摘の節に対処すること
    - 記録の形：雛形のパス（`${CLAUDE_SKILL_DIR}/templates/report.md`）と、表題に入れるタスクのIDと回数
    - 書き先：`tasks/<NN>_<slug>/worker-<n>.md`
    - 返答の形：`結論: <完了 | 判断待ち | 中断> / パス: <書き先>`の一行
- 評価者に渡す
    - 対象：該当タスクの成果物と最新の報告のパス。全体レビューでは成果物の一覧と各タスクの最新の報告のパス
    - 完了条件：該当タスクの完了条件と確かめ方。全体レビューでは指示書の完了条件
    - 制約：実行者に渡したものと同じ制約
    - 変えてよい範囲：該当タスクの触ってよい範囲に、他のタスクの成果物と触ってよい範囲、実行者の一時領域を加えたもの。全体レビューではすべてのタスクの触ってよい範囲と、実行者と評価者の一時領域
    - 読む資料：前回のレビューがあればそのパス
    - 一時領域：`tasks/<NN>_<slug>/tmp/reviewer-<n>/`。全体レビューでは`tmp/reviewer-<n>/`
    - 記録の形：雛形のパス（`${CLAUDE_SKILL_DIR}/templates/review.md`）と、表題に入れるタスクのID（全体レビューでは「全体」）と回数
    - 書き先：`tasks/<NN>_<slug>/reviewer-<n>.md`。全体レビューでは`reviewer-<n>.md`
    - 返答の形：`判定: <承認 | 差し戻し> / 指摘: <件数> / 提案: <件数> / パス: <書き先>`の一行

担当は記録を書き先に自分で書き、返答は返答の形の一行だけを返す。統括は返答で次の段を決め、記録の中身は手順が定める節だけを読む。

## レビューの規則

評価者は次を確かめ、いずれかに該当すれば差し戻し、すべて該当しなければ承認と判定する。

- 完了条件のいずれかが満たされていない、または現物で確かめられない
- 触ってよい範囲の外に変更がある
- 報告の記述が現物と一致しない（検証していないことを検証済みと書く、変更したファイルを報告に書いていない等）

該当しない指摘（改善の余地、好み）は提案として書き、判定に用いない。指摘と提案には根拠となる現物と確度（0から100。その内容が成り立つと判じる度合い）を付す。制約のために採られた手段と、制約のために変更されなかった点は、指摘にも提案にもならない。

## 境界

- 変えてよいのは、指示書の対象と範囲の内で、計画の触ってよい範囲に書いた場所だけである
- 作業の終点は指示書が定める。コミット、プッシュ、PRの作成、提出等の後処理は、指示書の完了条件または制約が求めていない限り行わない。求めていれば、全体レビューの承認後に統括が行う
- 案件ディレクトリの記録は消さない。中止した案件の記録も残す

## 問い方

依頼元への問いは一件ずつ行い、答えを記してから次へ進む。判断を求める問いには、問題とその影響範囲、原因、案（あれば複数）と各案の利害得失、推奨と根拠を添える。推奨は既定値ではなく、依頼元の答えに従う。答えは`plan.md`の裁定の節に、日時（`YYYY-MM-DD HH:MM:SS`）、問い、答えの形で記す。

## 停止条件

- 依頼元の答えまたは承認が得られない：問いを示したまま停止する。推測で補って進めない
- 担当の起動に失敗した、または返答のパスに記録が無い：失敗の内容（コマンドと応答）を示して停止する。統括が代わりに作業しない
- 中止の指示を受けた：案件の状態を中止にして完了日時を記し、経過にその時点の状況を記して停止する
