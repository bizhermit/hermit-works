# hw:execute

指示書を受け、対応方針を立てて依頼元の承認を得たうえで、実行計画を立て、計画のタスクごとに実行者に実施させ、評価者のレビューを経て成果物を仕上げ、依頼元が成果物を認めたら案件を完了にする。本スキルを実施する人物を統括と呼ぶ。統括は対応方針を立て、計画を立て、担当を起動し、判定し、依頼元と対話する。成果物は自分では作らない。

## 入力

- 引数：$ARGUMENTS
- 指示書：`hw:request`が作成した指示書、または`hw:request`以外の手段で書かれた指示書（人間が直接書いたGitHub Issue等）。引数が示すファイル、または運用で定められた外部トラッカーの課題
- 運用：定められた規則（`CLAUDE.md`、運用手順書等）のうち、外部トラッカーの使用を定めた記述
- 案件：止まった案件を再開するときの、案件ディレクトリ（`${CLAUDE_PROJECT_DIR}/.hw/cases/<案件>/`）のパス

引数が案件ディレクトリのパスなら、「再開」の節に従う。引数が無ければ、`${CLAUDE_PROJECT_DIR}/.hw/instructions/`にある指示書の一覧と、`${CLAUDE_PROJECT_DIR}/.hw/cases/`にある案件のうち状態が完了でも中止でもないものの一覧（案件ディレクトリと状態）を示し、どれを実行するか、またはどれを再開するかを問う。引数が指示書のパスでも案件ディレクトリのパスでもなければ、運用の記述に従って課題の本文を取得する。運用の記述に取得する手順が無ければ、依頼元に問う。指示書が定まったら、その指示書を写した案件（`plan.md`の「指示書」の欄が同じ出所を指すもの）のうち状態が完了でも中止でもないものがあるかを確かめる。あれば、その案件と状態を示し、再開するか新たな案件として始めるかを問う。

## 役割

- 統括：本スキルを実施する人物。計画を立て、担当を起動し、判定し、依頼元と対話する
- 実行者：`hw:worker`。計画の一つのタスクを行い、報告を返す
- 評価者：`hw:reviewer`。一つのタスクまたは案件全体の成果物を、完了条件、制約、変えてよい範囲に照らして現物で確かめ、レビューを返す。成果物を変えない

実行者と評価者をまとめて担当と呼ぶ。前回の内容は記録（報告、レビュー）で渡す。一つのタスクの実行者と評価者に同じ担当を使わない。

## 作業ディレクトリ

案件ごとに`${CLAUDE_PROJECT_DIR}/.hw/cases/<YYYYMMDD>_<slug>/`を作る。`<YYYYMMDD>`は着手日（`date +%Y%m%d`）、`<slug>`は指示書の表題を表すASCIIの小文字とハイフンからなる短い語である。同名のディレクトリが既にある場合は末尾に`-2`、`-3`と連番を付ける。

```text
<案件ディレクトリ>/
├── instruction.md        # 指示書の写し
├── plan.md               # 対応方針、実行計画と経過。雛形はtemplates/plan.md
├── reviewer-<n>.md       # 全体レビュー。雛形はtemplates/review.md
├── tmp/reviewer-<n>/     # 全体レビューの評価者の一時ファイル
└── tasks/<NN>_<slug>/    # タスクごとの記録
    ├── worker-<n>.md     # 実行者の報告。雛形はtemplates/report.md
    ├── reviewer-<n>.md   # 評価者のレビュー。雛形はtemplates/review.md
    └── tmp/              # 一時ファイル。実行者はworker-<n>/、評価者はreviewer-<n>/
```

`<NN>`はタスクの番号（`01`から）、`<n>`は回数（`1`から）である。記録のファイル名は、その記録を書いた役割を表す。実行者を起動するたびに報告の回数が1増え、評価者を起動するたびにレビューの回数が1増える。統括が行ったこと（問いと答え、対応方針の承認、担当の起動、報告の受領、判定、状態の変更）は、その都度`plan.md`の「経過」の節に日時（`YYYY-MM-DD HH:MM:SS`）を付けて書く。

## 手順

### 1. 指示書を読む

指示書を読み、案件ディレクトリを作り、`instruction.md`に全文を写す。指示書に現物を指す語（ファイル、画面、機能等）があれば、リポジトリ、または指示書が示す場所に実際にあるかを確かめる。確かめられないものは未確定事項として扱う。指示書に目的が無ければ、`hw:request`で目的を補うよう依頼元に示して停止する。指示書に完了条件が無いときは停止しない。完了条件は手順3で統括が指示書から割り出して「対応方針」の節に書き、依頼元が対応方針を承認するときに確かめる。

### 2. 未確定事項を解く

指示書の未確定事項と、依頼元にしか決められない事項を、一件ずつ依頼元に問う。指示書から定まらないが統括が決められる事項は問わず、手順3で「対応方針」の節に書く。答えは`plan.md`の「裁定」の節に書く。依頼元が後で決めるとした事項があれば、その事項に依らないタスクだけを計画し、依る部分は残論点として`plan.md`に書く。

### 3. 対応方針を立て、承認を得る

現状をどう変えれば目的を達成できるかを、[templates/plan.md](${CLAUDE_SKILL_DIR}/templates/plan.md)に従って`plan.md`の「対応方針」の節に書く。「対応方針」の節には次を書く。

- 未確定事項の裁定：手順2で依頼元が答えた事項と、指示書から定まらないが統括が決めた事項
- 完了条件と確かめ方：指示書に完了条件があればそれを写して確かめ方を添える。無ければ統括が目的から割り出した完了条件を、統括が割り出したものと分かる形で書き、確かめ方を添える。確かめ方を定められない完了条件があれば、承認を問う前に依頼元に示して言い直しを問う
- 変更の対象：どの現物（パス等）を変えるか。指示書の目的と、指示書に対象範囲や依頼元の意見があればそれを材料にする。指示書に無い現物をどう扱うかも書く
- 作業の場所と終点：作業する場所（ブランチ、ディレクトリ等）、起点のブランチ（作業ブランチを切った元のブランチ）、作業をどこまで行うか（作業の終点）
- 指示書に無い要件：目的の達成に要ると判断した要件を、統括が加えたものと分かる形で書く
- 検証の資源・権限・副作用：検証に使う資源、要る権限、検証で生じる副作用
- 委任の範囲：統括が依頼元に問わず裁定してよい事項
- 個別の対応案：対象ごとに、どう変えるか。文書（スキル、設計書、手順書等）を書き直すときは、書き直す文言そのものを書く

指示書に、どう対処するかについての依頼元の意見（どのファイルにどういう修正を行うか、対象範囲、完了条件等）があれば、それを対応方針の材料にする。

指示書に定めが無い事項は、対応方針で定める。指示書に定めが無いときは、権限は省略せず、委任の範囲はなしとする。

「対応方針」の節の全文を依頼元に示し、この方針で進めてよいかを問う。依頼元から修正を求められたら、「対応方針」の節に反映して再び示す。指示書に無い要件は、承認を得たものだけを加え、承認を得ていない要件は加えない。承認を得るまで手順4に進まない。

### 4. 計画を立てる

承認された対応方針をもとに作業をタスクに分け、[templates/plan.md](${CLAUDE_SKILL_DIR}/templates/plan.md)に従って`plan.md`を書く。計画については依頼元に承認を問わない。

- 目的、制約と境界は指示書の語で写し、完了条件は対応方針で定めたもの（指示書にあれば指示書の語で写したもの、無ければ統括が割り出したものと分かる形で書いたもの）を写し、統括が具体化した部分（確かめ方、パス）を書き足す
- タスクは、成果物と完了条件が一つに定まる単位に分ける。一つのタスクが担うことは一つにする
- タスクごとに、行うこと、成果物、完了条件と確かめ方、変えてよい範囲、依存を書く
- 完了条件は現物で確かめられる形（実行するコマンド、比べる対象、見る画面）で書く
- 対応方針で定めた完了条件のすべてが、いずれかのタスクの完了条件または全体レビューで確かめられることを確かめる。確かめられない条件は、対応方針の承認の前に問う（手順3）

計画を変える（タスクの追加、削除、完了条件や範囲の変更）とき、対応方針も変わるなら、変えた対応方針を依頼元に示して承認を得る。対応方針が変わらなければ、変えた内容を「経過」の節に書いて進む。

### 5. タスクを実行する

依存の順にタスクを進める。互いに依存せず、変えてよい範囲が重ならないタスクは同時に進めてよい。タスクごとに次を繰り返す。

1. 実行者を起動する
2. 返答の結論を見る。判断待ちなら、報告の「判断を求める事項」の節を読み、事項ごとに、委任の範囲の内なら統括が裁定して「裁定」の節に書き、委任の範囲の外なら依頼元に一件ずつ問い、答えを「裁定」の節に書く。そのうえで実行者を再び起動する。中断なら、報告の全文を読み、中断の原因となった事項を一件ずつ、「問い方」の手順に従って依頼元に問う。報告の「気づいたこと」は問わず、タスクが完了したときに扱う
3. 結論が完了なら、評価者を起動する
4. 判定が承認なら、タスクの状態を完了にする。レビューに提案があれば「提案」の節を、報告に気づいたことがあれば「気づいたこと」の節を読み、一件ずつ裁定する。対応方針を変えず、仕様の裁定を要しないもの（文言の食い違い、説明の不足、現物と合わない記述等）は、統括が採り入れるかを裁定して「裁定」の節に書き、採り入れるものはタスクを追加する。統括が裁定できないもの（仕様を定めるもの、対応方針が変わるもの）は、そこで止まり、依頼元に一件ずつ「問い方」の手順に従って問う。そのうえで次へ進む
5. 判定が差し戻しなら、レビューの「指摘」の節を読んで対応を決め、実行者を再び起動する。同じタスクの差し戻しが3回に達したら繰り返さず、レビューの指摘と経過を依頼元に示して判断を問う

統括が記録を読むのは、各手順が定める節だけである。節は、見出しを手がかりにその部分だけを抜き出して読む。抜き出した結果が空なら、記録の全文を読む。統括は成果物を自分で直さない。

### 6. 全体レビュー

すべてのタスクが完了したら評価者を起動し、対応方針で定めた完了条件のすべてを成果物に照らして確かめさせる。判定が差し戻しなら、全体レビューの「指摘」の節を読む。指摘ごとに、対応方針を変えずに成果物を直せるならタスクを追加して手順5で進め、対応方針が変わるなら変えた対応方針を依頼元に示して承認を得てからタスクを加える。完了したタスクは差し戻さない。追加したタスクがすべて完了したら、全体レビューを再び行う。判定が承認なら、手順7に進む。

### 7. 利用者レビューを受ける

全体レビューの「完了条件の検証」の節と「提案」の節を読む。提案を一件ずつ手順5の4と同じ基準で裁定し、採り入れるものはタスクを追加して手順6に戻る。統括が裁定できないものを残論点とする。`plan.md`の「結果」の節に、完了条件ごとの検証結果、成果物の一覧、残論点、全体レビューへのリンクを書く。案件の状態を利用者レビュー中にし、「経過」の節に書く。依頼元に、結論、成果物の一覧、完了条件の検証結果、残論点、案件ディレクトリのパスを示し、成果物を認めるか差し戻すかを問う。

- 依頼元が認めたら、「結果」の節に変更量を「`- 変更量: <ファイル数>ファイル、追加<行数>行、削除<行数>行`」の形で書く。値は、「変更の対象」に書いたパスごとに`.gitignore`の対象かを`git check-ignore -q -- <パス>`で確かめ（終了コード0なら対象）、対象でないものを`git add -N -- <パス>`で数える対象に加えたうえで、起点のブランチとの分岐点と作業ツリーの差分（`git diff --shortstat $(git merge-base <起点ブランチ> HEAD)`）から取り、gitの管理外なら「不明」と書く。値を取った後に、`git add -N`に与えたパスのステージを`git reset -q -- <パス>`で外す。指示書が求めているコミット等の後処理を行い、その結果を「結果」の節に書き足す。コミットしたときは「`- コミット: <ハッシュ>`」の形で書く。案件の状態を完了にして完了日時を書く
- 依頼元が差し戻したら（残論点を採り入れると決めたときも同じ）、差し戻しの内容を「裁定」の節に書き、案件の状態を実行中にする。採り入れると決めた提案は、一件ずつ「`採り入れる提案: <レビューの相対パス> <番号>`」の形で書く。差し戻しの内容ごとに、手順6と同じく、対応方針を変えずに成果物を直せるならタスクを追加し、対応方針が変わるなら承認を得てからタスクを加える。完了したタスクは差し戻さない。そのうえで手順5に戻り、全体レビューと利用者レビューを再び行う

## 再開

止まった案件（状態が完了でも中止でもない案件）は、案件ディレクトリの記録から続きを進める。再開の入口は「入力」の節に定める。

1. `plan.md`を読み、状態、「経過」の節の最後の項、各タスクの状態から、どこで止まったかを割り出す。「経過」の節に、再開したことと止まった場所を書く
2. 「経過」の節の最後の項が、依頼元の答えまたは承認を待つ問いであれば、その問いを再び示し、答えを得てから進める
3. 状態に応じて続きを進める
    - 計画中：「対応方針」の節が無ければ手順2から、あれば手順3の承認を問うところから、承認を得たことが「経過」の節にあれば手順4から進める
    - 実行中：手順5をタスクの状態から続ける。未着手のタスクはそのまま始める。実行中またはレビュー中のタスクは、「経過」の節に書いた最後の起動の回の記録が書き先にあればそれを受領して続きを行い、無ければ担当を再び起動する（回数を1増やす）。判断待ちのタスクは、報告の「判断を求める事項」の節を読んで問いを再び示す。差し戻しのタスクは実行者を再び起動する。すべてのタスクが完了していれば手順6から進める
    - 利用者レビュー中：「結果」の節を依頼元に示し、成果物を認めるか差し戻すかを再び問う（手順7）
    - 完了または中止：再開しない

再開の前に書いた記録は消さず、続きはその後に書き足す。

## 担当の起動

担当は`Agent`ツールで起動する。`subagent_type`は実行者が`hw:worker`、評価者が`hw:reviewer`である。作業に要るものは`plan.md`から取り出してプロンプトに書き、`plan.md`と案件ディレクトリの構成は渡さない。

- 実行者に渡す
    - 作業：該当タスクの行うことと成果物
    - 目的：指示書の目的
    - 完了条件：該当タスクの完了条件と確かめ方
    - 制約：指示書の制約と、コミット、プッシュ、PRの作成を行わないこと
    - 変えてよい範囲：該当タスクの変えてよい範囲
    - 一時領域：`tasks/<NN>_<slug>/tmp/worker-<n>/`
    - 読む資料：依存するタスクの成果物と最新の報告のパス。差し戻しであれば前回の報告のパス
    - 指摘：差し戻しであれば前回のレビューのパスと、その「指摘」の節に対処すること
    - 記録の形：雛形のパス（`${CLAUDE_SKILL_DIR}/templates/report.md`）と、表題に入れるタスクのIDと回数
    - 書き先：`<案件ディレクトリ>/tasks/<NN>_<slug>/worker-<n>.md`。案件ディレクトリからの相対パスではなく、`.hw/cases/<案件>/`を含むパスで書く
    - 返答の形：`結論: <完了 | 判断待ち | 中断> / パス: <書き先>`の一行
- 評価者に渡す
    - 対象：該当タスクの成果物と最新の報告のパス。全体レビューでは成果物の一覧と各タスクの最新の報告のパス
    - 完了条件：該当タスクの完了条件と確かめ方。全体レビューでは対応方針で定めた完了条件
    - 制約：実行者に渡したものと同じ制約
    - 変えてよい範囲：該当タスクの変えてよい範囲に、他のタスクの成果物と変えてよい範囲、実行者の一時領域を加えたもの。全体レビューではすべてのタスクの変えてよい範囲と、実行者と評価者の一時領域
    - 読む資料：前回のレビューがあればそのパス
    - 一時領域：`tasks/<NN>_<slug>/tmp/reviewer-<n>/`。全体レビューでは`tmp/reviewer-<n>/`
    - 記録の形：雛形のパス（`${CLAUDE_SKILL_DIR}/templates/review.md`）と、表題に入れるタスクのID（全体レビューでは「全体」）と回数
    - 書き先：`<案件ディレクトリ>/tasks/<NN>_<slug>/reviewer-<n>.md`。全体レビューでは`<案件ディレクトリ>/reviewer-<n>.md`。案件ディレクトリからの相対パスではなく、`.hw/cases/<案件>/`を含むパスで書く
    - 返答の形：`判定: <承認 | 差し戻し> / 指摘: <件数> / 提案: <件数> / パス: <書き先>`の一行

担当は記録を書き先に自分で書き、返答は返答の形の一行だけを返す。統括は返答を見て次に何をするかを決め、記録の中身は手順が定める節だけを読む。

## レビューの規則

評価者は次を確かめ、いずれかに該当すれば差し戻し、どれにも該当しなければ承認と判定する。

- 完了条件のいずれかが満たされていない、または現物で確かめられない
- 変えてよい範囲の外に変更がある
- 報告の記述が現物と一致しない（検証していないことを検証済みと書く、変更したファイルを報告に書いていない等）

該当しない指摘（改善の余地、好み）は提案として書き、判定に用いない。指摘と提案には根拠となる現物と確度（0から100。その内容が成り立つと判断する度合い）を付ける。制約のために選ばれた手段と、制約のために変更されなかった点は、指摘にも提案にもしない。

## 境界

- 変えてよいのは、指示書の制約の内で、計画の変えてよい範囲に書いた場所だけである
- 作業の終点は指示書が定める。コミット、プッシュ、PRの作成、提出等の後処理は、指示書が求めていない限り行わない。求めていれば、全体レビューの承認後に統括が行う
- 案件ディレクトリの記録は消さない。中止した案件の記録も残す
- 完了または中止にした案件の状態は変えない。完了した案件の成果物を変えるには、新たな指示書で別の案件にする

## 裁定の記録

依頼元への問いは一件ずつ行い、答えを書いてから次へ進む。答えは`plan.md`の「裁定」の節に、日時（`YYYY-MM-DD HH:MM:SS`）、問い、答えの形で書く。統括が自分で裁定した事項（手順5の2の委任の範囲の内の裁定、手順5の4の提案と気づいたことの裁定、手順7の提案の裁定）は、同じ節に、日時（`YYYY-MM-DD HH:MM:SS`）、「統括の裁定」の語、事項、裁定と理由の形で書く。

## 停止条件

- 依頼元の答えまたは承認が得られない：問いを示したまま停止する。推測で補って進めない。止まった案件は「再開」の節に従って続ける
- 担当の起動に失敗した、または返答のパスに記録が無い：失敗の内容（コマンドと応答）を示して停止する。統括が代わりに作業しない
- 中止の指示を受けた：案件の状態を中止にして完了日時を書き、「経過」の節にその時点の状況を書いて停止する
