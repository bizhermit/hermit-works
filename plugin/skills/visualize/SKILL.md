# hw:visualize

`hw:execute`の案件記録を一つ指定すると、案件ファイルを読んで分析項目ごとの値を`<案件>.json`に書き、[scripts/visualize.py](${CLAUDE_SKILL_DIR}/scripts/visualize.py)を実行して、その案件で使った資源、進め方、質をHTMLに可視化し、案件一覧の`index.html`を作り直す。HTMLは自分で書かない。

## 入力

- 引数：$ARGUMENTS。案件ディレクトリのパス、または案件の親ディレクトリのパス。親ディレクトリなら、その直下の全案件を可視化する
    - 案件ディレクトリ：`plan.md`を持つディレクトリ。既定の置き場所は`${CLAUDE_PROJECT_DIR}/.hw/cases/<案件>/`
    - 親ディレクトリ：`plan.md`が無く、直下に`plan.md`を持つディレクトリが一つ以上あるディレクトリ。名前と置き場所を問わない。既定の置き場所は`${CLAUDE_PROJECT_DIR}/.hw/cases/`
- 案件ファイル：案件ディレクトリの次のファイル。読んで`<案件>.json`に値を書く
    - `plan.md`
    - `tasks/*/`の報告（`worker-<n>.md`。古い案件では`report-<n>.md`）とレビュー（`reviewer-<n>.md`。古い案件では`review-<n>.md`）
    - 案件ディレクトリ直下の全体レビュー（`reviewer-<n>.md`。古い案件では`review-<n>.md`）
- セッション記録：Claude Codeの設定ディレクトリ（`${CLAUDE_CONFIG_DIR}`、無ければ`~/.claude`）の下の`projects/`。スクリプトが読む
- 単価表：[pricing.json](${CLAUDE_SKILL_DIR}/pricing.json)。利用者が書き換えてよい
- JSONの形：[json-format.md](${CLAUDE_SKILL_DIR}/json-format.md)。`<案件>.json`の項目、記録に無いときの書き方、記入例が載る

## 出力

`${CLAUDE_PROJECT_DIR}/.hw/analysis/`に次のファイルができる。

- `<案件>.json`：手順3で案件ファイルから取り出して書く分析項目ごとの値と、スクリプトがセッション記録と単価表から取って`script`の下に書き足す値が載る
- `<案件>.html`：スクリプトが書く。案件一覧（`index.html`）へのリンクと表題の後に、次の節が載る。表は基本情報の節とタスク一覧の節だけである
    - 概要：目的
    - 基本情報：状態、着手日時、完了日時（`<案件>.json`の`finished`が`null`なら「（実行中）」）、所要時間（全体、AI、待機）、セッションID、作業ブランチ（複数なら箇条書き）を三列の表で載せる。所要時間は「所要時間」の見出しを三行に結合し、「全体」「AI」「待機」の見出しと値を一行ずつ並べる。ほかの行は見出しを二列に結合する
    - 費用：合計のトークン量と合計の費用（米ドル）を大きなカードで載せ、担当（統括、実行者、評価者）ごとの費用、トークン量の合計、使ったモデルを小さなカードで並べる。その下に、トークン量（入力、出力、キャッシュ作成、キャッシュ読み取り）と費用を、担当ごと、モデルごと、タスクごとの棒グラフで載せ、数値を棒の横に添える。担当ごとの棒グラフには、トークン量の合計も載せる。単価の日付と出所、費用の求め方、標準以外の呼び出しの数は、短い注記で載る
    - 処理：全体、AI、待機の所要時間（待機には待機の区間の件数を添える）を大きなカードで載せ、担当の起動回数（実行者、評価者、全体レビュー）と並列か直列かを小さなカードで並べる。その下に、着手日時から完了日時（無ければ可視化した日時）までの時系列の図。行は、段階（対応方針の作成、計画、全体レビュー、利用者レビュー等）、タスクごとの実行者と評価者の起動、全体レビューの起動で、まとまり（方針と計画、タスクの実行、全体レビュー、利用者レビュー）の間に区切り線を引き、裁定の時点と待機の区間も描く。始めか終わりが`null`の段階と、開始時刻か終了時刻が不明の担当の起動は図に描かず、図の下の注記の「図に描けなかったもの」に載る。図の後に、担当の起動が無く10分以上空いた区間の箇条書き、段階とタスクの流れのフローチャート、初期状態は閉じた経過が載る。フローチャートは、上から下へ時間の順に、段階（`phases`の区間）とタスクのノードを並べ、矢印でつなぐ。ノードの種類（段階、タスク、全体レビュー、利用者レビュー）は枠の色と角の丸み（タスクのノードは角を小さく丸め、他のノードは大きく丸める）で、矢印の種類（流れ、依存、差し戻しで戻った流れ）は線の色と形で見分け、凡例が載る。段階は開始日時の順に一行ずつ並び、区間と差し戻しの印が添えられる。タスクは、着手した時刻以後に始まった最初の全体レビューか利用者レビューの段階の直前に、依存の段ごとに一行にして並び、担当の起動回数と差し戻し回数が添えられる。依存の矢印は`depends`の依存ごとに依存先から依存するタスクへ、差し戻しの矢印は、差し戻したレビューの段階から、差し戻したタスクと、そのレビューの後ろで次のレビューの段階までに置いたタスクへ（どちらも無ければ次のノードへ）引かれる。全体レビューの差し戻しはn回目の全体レビューの段階から、利用者レビューの差し戻しは差し戻した日時までに終わった全体レビューか利用者レビューの段階のうち最後に終わったものから引かれ、元が全体レビューの段階なら、その段階に「利用者が差戻」と添えられる。開始日時の無い段階、`depends`が`null`のタスクの依存、元か先が図に無い差し戻しは、図の下の注記の「図に置けなかったもの」に載る
    - タスク一覧（初期状態は閉じている）：タスクごとに、タスクのIDと名前の見出しの下に字下げして、タスクの概要（`<案件>.json`の`tasks`の`work`）と、横に並べた二つの領域が載る。一つは「タスク」の見出しの下の二列の表（状態、開始日時、完了日時、所要時間（トータル）、所要時間（AI）、所要時間（待機時間）、差戻回数、依存）、もう一つは「担当」の見出しの下に担当の起動ごとの二列の表（役割、agent、model、effort）を組に分けて並べたものである。組は、担当の起動を時刻の順に並べ、評価者の起動の後に来る実行者の起動ごとに始まる。評価者の起動の前に続く実行者の起動は同じ組に入り、最初の実行者の起動より前の評価者の起動は初回の組に入る。組は縦に並び、初回の組には見出しが無く、2組目からは組の上に「差戻1」「差戻2」…の見出しが載る。組の中の表は横に並ぶ。画面の幅が足りなければ、二つの領域と組の中の表は折り返して縦に並ぶ。依存の値は、依存するタスクがあれば「T1、T2」の形、`depends`が`[]`なら「なし」、`null`なら「不明」とその理由である。開始日時はそのタスクの担当の最初の起動の開始時刻、完了日時は最後の起動の終了時刻である。二つの領域の下に、成果物と変えてよい範囲を箇条書きで載せる
    - レビューと差し戻し（初期状態は閉じている）：タスクごとの差し戻しの回数、全体レビューの回数、完了から実行中に戻した回数、対応方針の変更の回数、差し戻しの理由、裁定、評価者の提案の数と採り入れた数、変更量、取れなかった指標とその理由
- `index.html`：スクリプトが書く。`${CLAUDE_PROJECT_DIR}/.hw/analysis/`に`<案件>.json`がある全案件の一覧の表と、「指標の比較」（初期状態は閉じている）が載る。一覧の表の先頭の列は、1から並ぶ番号である。一覧の表の表題は、その案件の`<案件>.html`へのリンクである。「指標の比較」には、指標ごとに案件を並べた棒グラフと、案件ごとの変更量（ファイル数、追加行数、削除行数）の箇条書きが載る。棒グラフの案件名は、その案件の`<案件>.html`へのリンクである

## 手順

1. 引数を確かめる。
    - 引数が無ければ、`${CLAUDE_PROJECT_DIR}/.hw/cases/`にある案件の一覧（案件ディレクトリの名前と、`plan.md`の「状態」の値）を示し、どれを可視化するかを問う。答えを引数にする。
    - 引数が案件ディレクトリでも親ディレクトリでもなければ、その旨を示して停止する。
2. `python3 --version`を実行し、`python3`があるかを確かめる。無ければ、その旨を示して停止する。
3. 案件ごとに、案件ファイルを読み、`json-format.md`の形で`${CLAUDE_PROJECT_DIR}/.hw/analysis/<案件>.json`を書く。引数が親ディレクトリなら、その直下の案件ディレクトリごとに行う。利用者が`--out <出力先>`を指定したときは、`<出力先>/<案件>.json`に書く。書き先のディレクトリが無ければ作る。
    - `json-format.md`の「実施者が書く項目」の表の項目を、分析項目ごとに案件ファイルの中から値を取り出して書く。`script`は書かない。
    - 記録の形が雛形と違っても（欄の名前が違う、裁定が番号付きの項で書かれている、報告やレビューのファイル名が古い等）、同じ情報が記録にあれば取り出す。
    - 段階（`phases`）は、`json-format.md`の「段階」の節に従い、「経過」と「裁定」の節から段階ごとに始めと終わりの日時を読み取って書く。タスクの実行の区間は書かない。段階を一つも読み取れなければ、`[]`を書き、`unknown`に`phases`と理由を書く。
    - 記録に無い項目のうち、null可の項目は、値を`null`にし、`unknown`に項目の場所と理由（どの節を探して無かったか）を書く。書き方は`json-format.md`の「記録に無いときの書き方」に従う。要素が無いと記録から分かる配列は、`null`にせず`[]`にする。
    - 採り入れた提案の数（`proposals_adopted`）と変更量（`change`）は、`basis`に根拠を書く。根拠の書き方は`json-format.md`の「採り入れた提案」と「変更量」の節に従う。
    - 既に`<案件>.json`があれば、`script`を除く項目を案件ファイルから取り出し直して書き直す。`script`は変えない。
4. スクリプトを実行する。

    ```
    python3 ${CLAUDE_SKILL_DIR}/scripts/visualize.py <引数>
    ```

    出力先、設定ディレクトリ、単価表は既定のまま実行する。オプション（`--out <出力先>`、`--config-dir <設定ディレクトリ>`、`--pricing <単価表>`）は、利用者が指定したときだけ付ける。

    - 終了コードが0以外で、標準エラーに「の形がjson-format.mdと違う」または「をJSONとして読めない」とあれば、標準エラーが示す項目を`<案件>.json`で直し、再び実行する。
    - 終了コードが0以外で、標準エラーがそれ以外の誤りを示していれば、停止条件に従って停止する。
5. スクリプトの標準出力の「出力したファイル:」の下の行から出力したファイルのパスを、「取れなかった指標:」の下の行から取れなかった指標とその理由を読み、依頼元に示す。取れなかった指標は、案件ファイルに無かったものと、セッション記録から取れなかったものの両方を示す。「飛ばした案件:」の行があれば、その案件と理由も示す。

## 停止条件

- `python3`が無い：その旨を示して停止する
- 引数が案件ディレクトリでも親ディレクトリでもない：その旨を示して停止する
- スクリプトが形の誤り以外の理由で0以外の終了コードで終わった：標準エラーの内容を示して停止する。HTMLを代わりに書かない
