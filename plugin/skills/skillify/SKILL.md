# hw:skillify

`hw:execute`の案件記録を分析し、複数の案件に繰り返し現れるパターンを割り出し、依頼元が選んだものをプロジェクトのスキル（`${CLAUDE_PROJECT_DIR}/.claude/skills/`に置くスキル）にするための指示書を作る。本スキルが担うのは指示書を作るまでであり、スキルを作るのは`hw:execute`に任せる。繰り返しが無ければ、スキルにするのを見送ると報告する。

## 入力

- 案件記録：`${CLAUDE_PROJECT_DIR}/.hw/cases/<案件>/`のうち、`plan.md`の状態が完了のもの。読むのは`instruction.md`（目的、依頼元の意見）、`plan.md`（「対応方針」の節の変更の対象、完了条件と確かめ方、検証の資源・権限・副作用、委任の範囲と、「タスク」の節の作業、成果物、完了条件）、各タスクの最新の`worker-<n>.md`（行った作業）
- 既存スキル：`${CLAUDE_PROJECT_DIR}/.claude/skills/*/SKILL.md`。プラグインのスキルと利用者個人のスキルは対象にしない
- 運用：定められた規則（`CLAUDE.md`、運用手順書等）のうち、外部トラッカーの使用を定めた記述

## 用語

- 種類：案件の分類。`instruction.md`の目的と対象から、何をどう変える案件かで分ける。種類の一覧は事前に持たず、記録から割り出す
- タスクの並び：一つの案件の`plan.md`のタスクを、行うことと成果物の形で順に並べたもの
- パターン：複数の案件に繰り返し現れるもの。次の三つの水準がある
    - 種類のパターン：同じ種類の案件が複数あり、対応方針（変更の対象、完了条件と確かめ方、検証の資源と権限）とタスクの並びが揃うもの
    - タスクのパターン：同じ行うことと同じ成果物の形を持つタスク、またはその並びが、複数の案件に現れたもの
    - 組み合わせのパターン：複数の種類にまたがる案件が、同じ種類の組で複数あるもの
- 頻度：パターンが現れた案件の数
- 候補：頻度が2以上のパターン
- 入口：利用者が呼ぶスキル。種類のスキルとラッパーがこれにあたる
- 部品：他のスキルから呼ばれるスキル
- ラッパー：種類のスキルを順に呼ぶだけで、手順を持たないスキル

## 粒度

スキルが増えるほど、使う側はどれを使えばよいか分からなくなり、起動のたびに全スキルの説明がコンテキストに並ぶコストも増える。候補は一つずつではなく、次の規則でスキルの構成として組んでから示す。

- 種類のパターンは、種類ごとに一つのスキルにする。入口になる
- タスクのパターンは、二つ以上の種類にまたがって現れるときだけ、部品にする。一つの種類の中にしか現れないなら、その種類のスキルの手順の一つとして含め、単独のスキルにしない
- 組み合わせのパターンは、その組み合わせ自体が複数の案件に現れるときだけ、ラッパーにする。ラッパーは種類のスキルを順に呼ぶだけで、手順を持たない
- 一覧は構成として示す。入口と部品を分け、スキルの総数と、既にある`.claude/skills/`のスキルの数を添える。依頼元が選ばなかった部品は、呼ぶ側のスキルの手順に含める

## 手順

1. 案件記録を読む。完了した案件が無ければ、その旨を報告して終わる。
2. 仕分ける。案件ごとに`instruction.md`の目的と対象を読み、種類に分ける。複数の種類にまたがる案件は、その種類の組を書く。
3. パターンを割り出す。種類ごとに、各案件の対応方針とタスクの並びを読み比べ、揃う部分から種類のパターンを数える。種類をまたいで、同じ行うことと成果物の形を持つタスクを集め、タスクのパターンを数える。同じ種類の組にまたがる案件が複数あれば、組み合わせのパターンを数える。
4. 既存スキルと照らす。候補ごとに、`.claude/skills/`のスキルの手順と読み比べ、扱いを決める。
    - 新規：同じ手順を担うスキルが無い
    - 変更：同じ手順を担うスキルがあるが、案件記録にそのスキルに無い手順や条件分岐がある
    - スルー：同じ手順を担うスキルがあり、差が無い。一覧には載せるが、指示書は作らない
5. 候補が無い、または候補がすべてスルーなら、スキルにするのを見送ると報告して終わる。報告には、仕分けの結果（案件と種類）、割り出したパターンと頻度、候補が無い理由（頻度が2未満、または既存スキルで済む）を書く。
6. 粒度の規則で候補をスキルの構成として組み、入口と部品に分けて示し、進める候補を問う。候補は頻度順に並べる。各候補には、パターンの名前と水準、頻度と現れた案件、手順（種類のスキルは対応方針とタスクの並び、部品は行うことと成果物、ラッパーは呼ぶ順）、呼ぶスキルと呼ばれるスキル、扱い（新規、変更、スルー）、変更なら対象のスキルとそのスキルに無い手順や条件分岐を書く。
7. 選ばれた候補ごとに指示書の草案を組み、出力先とともに依頼元に示し、この内容で作成してよいかを問う。修正があれば反映して再び示す。承認を得るまで出力しない。
8. 出力先へ出力し、作成した課題のURLまたはファイルのパスを報告する。

## 指示書

雛形は`hw:request`と同じ[../request/templates/instruction.md](${CLAUDE_SKILL_DIR}/../request/templates/instruction.md)である。候補1件につき指示書1通を作る。

- 表題：新規なら「<パターンの名前>の手順をプロジェクトのスキル`<name>`にする」、変更なら「プロジェクトのスキル`<name>`に<手順または条件分岐>を加える」の形で書く
- 目的：新規なら、そのパターンの手順を`.claude/skills/<name>/SKILL.md`として用意し、同じ手順を案件ごとに計画し直さずに済むようにすること。変更なら、既存のスキルに案件記録で繰り返された手順や条件分岐を加えること
- 経緯と理由：パターンを割り出した根拠。水準、現れた案件とタスク、頻度、既存スキルとの照合の結果、粒度の規則でどう組んだか（呼ぶ側のスキルの手順に含めた部品があればそれも）
- 依頼元の意見：手順の案（種類のスキルは対応方針の変更の対象、完了条件と確かめ方、検証の資源と権限と、該当するタスクの最新の報告の行った作業をもとに書いた手順。部品は行うことと成果物をもとに書いた手順。ラッパーは呼ぶスキルとその順）、置き場（`.claude/skills/<name>/SKILL.md`）、変更なら変える箇所。手順の案は依頼元が承認するときに確かめた内容として書く
- 制約：次の二つを書く。依頼元が示した制約があればそれも書く
    - 作るスキルはこのプラグインに依存しない。プラグインのスキル（`hw:request`、`hw:execute`）、エージェント（`hw:worker`、`hw:reviewer`）、フック、雛形、`.hw/`の記録を参照せず、単独で動く。理由は、プラグインは必ずしもチームで入れているとは限らず、個人で使っている場合に共有すると使えないスキルになるためである
    - 依存。部品なら呼ぶ側のスキル、種類のスキルとラッパーなら呼ぶスキルと、先にそのスキルが要ること
- 未確定事項：問うても定まらなかった事項と、依頼元が後で決めるとした事項。無ければ「なし」

## 出力先

次の順で決める。上位で定まれば下位は参照しない。

1. 運用：定められた規則が外部トラッカーの使用を定めていれば、そのトラッカー
2. 既定：`${CLAUDE_PROJECT_DIR}/.hw/instructions/<YYYYMMDD>_<slug>.md`

既定のファイルの作り方（`<YYYYMMDD>`、`<slug>`、同名のときの連番、ディレクトリの作成）は、`hw:request`の[SKILL.md](${CLAUDE_SKILL_DIR}/../request/SKILL.md)の「出力先」の節と同じである。外部トラッカーへの課題の作成手順は運用が定めるものであり、本スキルは定めない。運用の記述に無い事項は依頼元に問う。

## 停止条件

- 依頼元の答えまたは承認が得られない：問いを示したまま停止する。推測で補って進めない
- 課題の作成に失敗した：失敗の内容（コマンドと応答）と、指示書の本文をそのまま示して停止する。別の出力先へ独断で出力しない
