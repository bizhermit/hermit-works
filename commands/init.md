---

hermit-works 組織の初期セットアップを実施します。本コマンドは導入直後の実行を想定していますが、
何度実行しても安全です（既存の成果物は上書きせず、更新として扱います）。

## 手順
1. **現状確認**: `.hw/` と既存マップ（`repo-map.md` / `conventions.md`）の有無を確認する（手順5の報告・チーム共有判定に用いる）。手順3・4（`hw:repo-map`・`hw:conventions`）は各スキルの `context: fork` によりフォーク先が実行するため、フォーク先は呼び出し元の会話履歴を持たず、ここでの新規/更新の判定結果は引き継がれない。各スキルが手順の冒頭で対象ファイルの有無を自力で再確認して新規/更新を判定するため、結果は一致する想定だが、手順5で報告する差分は各スキルの出力に従う。あわせて、コミット済みの `.claude/settings.json` に hermit-works のプラグイン設定が含まれるかを確認する（含まれる場合はチーム共有されている可能性が高く、個人用の `.claude/settings.local.json` のみに設定がある場合は個人利用の可能性が高いという目安とし、いずれにも該当せず判定できない場合は断定せず、最終判断は手順5で利用者に確認事項として問う）。`.hw/tracker.md` が追跡対象としてコミットされている場合も、チーム共有の目安に加える。
2. **作業ディレクトリの作成**: README「作業ディレクトリ規約」の構成に従い、`.hw/` 配下に `plans/` `reports/` `docs/` を作成する（空ディレクトリには `.gitkeep` を置く）。`routines.md` は `/hw:routine` が登録時に作成するため、ここでは作らない。`decisions.md` は
統括（mgmt-coordinator）が判断記録の初回発生時に作成するため、これも作らない。`procedures/` は初回蒸留時に統括（mgmt-coordinator）が作成するため、これも作らない。
3. **プロジェクト構成マップの整備**: hw:repo-map スキルの手順で `.hw/repo-map.md` を作成・更新する。
4. **利用者資材マップの整備**: hw:conventions スキルの手順で `.hw/conventions.md` を作成・更新する。
5. **報告と次の案内**: 以下を既定の言語（利用者側に言語規約があればそれに従い、なければ日本語）でまとめて報告する。
   - 作成・更新した資材の一覧（新規/更新の別、更新の場合は差分）
   - 検出したプロジェクト数と利用者側資材の概況
   - 既存のAI資材（CLAUDE.md・独自のスキル/コマンド/エージェント・他ツール向け資材）を検出した場合は、`/hw:optimize-assets` による hermit-works との適合性分析・整理を案内する
   - 利用者資材マップの「気づき」欄に未整理・矛盾の疑いを記載した場合は、`/hw:audit-assets` によるレビュー・是正を案内する（`/hw:optimize-assets` も案内する場合は、構成の最適化を先に行う推奨順序であることを添える）
   - 利用側の CLAUDE.md に「一次受けの振り分け方針」（コマンド未指定のプロンプトを内容に応じて `/hw:request` のフローに流すか直接対応するかの基準）が未記載の場合は、以下の趣旨の追記を提案する（**利用者の承認なしに追記しない**）
     > コマンド・スキル・エージェントの指定がないプロンプトは、内容を見て次のように扱う。コード変更を伴う依頼や複数工程・複数プロジェクトにまたがる依頼は `/hw:request` のフローに準じて対応し、質問・相談・軽い調査は直接対応してよい（専門的な分析を要する調査は `/hw:request` に流す）。軽微な1ファイル修正も直接対応してよいが、認証・認可・秘密情報・公開範囲・データスキーマ・課金等高リスク箇所に触れる場合は `/hw:request` に流す。迷う場合は、どちらで進めるかを一言添えてから着手する。
   - 利用側の CLAUDE.md に「記録先の使い分け」（チーム共有すべき事実と個人メモリの向き先）が未記載の場合は、以下の趣旨の追記を提案する（**利用者の承認なしに追記しない**）
     > チーム共有すべき事実（決定・規約・運用ルール・案件の背景）は個人メモリ（Claude Code の自動メモリ）でなく `.hw/` 配下（`decisions.md` / `conventions.md` / `docs/` 等）へ記録する。個人メモリは本人固有の好み・作業スタイル（個人のローカルな主観）に限る。特に利用者から指摘・訂正・裁定を受けて記録するときは、個人メモリへ書き込む前に「チーム共有すべき内容か」を判断する。共有すべき内容のうち、既存の規約・手順の誤り・不足に起因するものは当該資材（CLAUDE.md・スキル・コマンド・業務手順等）の修正を第一候補とし、資材に紐づかない決定・事実は `.hw/` 配下へ記録する。資材の修正は通常の変更フローに従い、迷う場合は共有側に倒すか利用者に確認する。既存の個人メモリに共有すべき内容を見つけたときも同様に判断して反映する（資材修正または `.hw/` への転記）。
   - **一括提案（決めたいものだけでよい）**: 手順4の利用者資材マップに、報告言語規約・品質ゲートの水準（レベル定義・レベル判定基準・差し戻し上限・レビューの重さ）の記載が見つからない場合、それぞれ「利用者が決められる項目であり、決めなくても既定値のまま動く」ことと既定値を提示する（報告言語の既定は日本語。品質ゲートの水準の既定は `agents/mgmt-coordinator.md`「品質ゲートの適用判定」節。sec-audit/sec-privacy の起動トリガーと生成者・評価者を分離する原則は提案対象外）。この場で決めたい項目だけを聞き、決まったものは `agents/mgmt-coordinator.md`「作業方針」の昇華の定めに従ってチーム共有物（移動先は固定しない）へ記録する提案を行う（**利用者の承認なしに追記しない**。`.hw/conventions.md` へは実体でなく索引のみ追記する）。決めない項目は既定のまま作業を進めてよく、実際にその項目が必要になった作業（該当する報告・品質ゲート判定）の場でエージェントが改めて提案する。セットアップの場で全項目の確定を求めない（机上でのルール確定を推し進めない）。
   - 次の一歩の案内: 案件の開始は `/hw:request`、定期実行のセットアップは `/hw:routine`、組織（誰に何を頼めるか）の把握は `/hw:show-org`。外部進捗管理ツール連携のセットアップは `hw:tracker-setup`。利用者側資材の整理は `/hw:optimize-assets`（構成の最適化）→ `/hw:audit-assets`（品質のレビュー・是正）の順で利用できる旨も添える（README「既存のAI環境がある場合の導入手順」の推奨順序）。開発文書（仕様書・コーディング規約・README等）の不足・陳腐化が疑われる場合は、ドラフトを作成して承認後に配置する `/hw:draft-docs` も案内する
   - `.hw/` をコミット対象としてチームで共有するかは利用者の方針によるため、手順1の確認結果を踏まえて次のいずれかを行う
     - チーム共有されていると判断できる場合: コミット対象とする方針でよいか確認事項として提示する（方針自体はここでは決めない）。あわせて、`.hw/reports/standup*` と `.hw/reports/report-*` はいずれも実行のたびに再生成される時点レポートでコミット・共有の価値が薄いため、`.gitignore` への追加を提案する。ただし `report-*`（定期レポート）はチームで健全性を共有したい場合に価値があり得るため、一括ではなくパターンごとに個別に追加可否を選べる形で提案する（**利用者の承認なしに追記しない**）
       > /.hw/reports/standup*
       > /.hw/reports/report-*

       既に該当レポートがコミット済みの場合は、承認されたパターンについて `git rm --cached` による追跡解除もあわせて提案する（削除系操作のため承認必須）
     - チーム共有されていないと思われ、かつ利用者の `.gitignore` に `/.hw/` 相当の記載がない場合: `.gitignore` への追加を提案する（**利用者の承認なしに追記しない**）
       > /.hw/

       追加を承認した場合、手順2で作成した `.gitkeep` は追跡対象外となり本来の役割（空ディレクトリの保持）が不要になるが、そのまま残しても支障はない旨を添える
   - 上記のいずれの場合であっても、tracker 設定がある場合は `.hw/` をコミット対象とする既定を提示し（公開リポジトリのときのみスナップショットの分離要否を確認する）、`.hw/local/` は常に `.gitignore` へ追加する提案を行う（承認なしに追記しない）。
   - URL区切り: 利用者向け出力・成果物文書に URL を含める場合は、markdown リンク `[表示名](URL)` または `<URL>` を優先し、裸 URL を書くときは前後を空白・改行で区切り、直後に句読点・助詞・装飾記号（`**` 強調や全角括弧等）を直接続けない（AI間の内部報告は対象外）。

手順2〜4はいずれも判断を伴わない機械的な調査・整形作業です。手順2はこのコマンドの実行主体が直接実施します。
手順3・4（`hw:repo-map`・`hw:conventions`）は各スキルの frontmatter（`context: fork`）に従い専用の
サブエージェント内で完結させます（専任の担当エージェントへの個別委任ではなく、実行コンテキストの分離）。
フォークの実行に失敗した場合は、各スキルの定めに従い実行主体が直接実施してフォールバックします。
